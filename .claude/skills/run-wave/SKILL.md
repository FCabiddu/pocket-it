## Run-wave — launch everything that is ready, review it once, stop

Runs in the main session. The decision of *what* to launch is made by a script, not by you; your job is to turn its output into Agent calls, wait, run one review, and report. Keep the session thin: no reading of task files, TADs or diffs here — that is the agents' work.

Arguments (optional): `$ARGUMENTS` — e.g. `dry-run`, `draft` (review only, no merge), or `only T-3.1.1, T-3.2.1`.

### 1. Pre-flight (zero tokens)
```bash
bash ~/.claude/agents/pocket-it/bin/doctor.sh && bash ~/.claude/agents/pocket-it/bin/next-wave.sh
```
Any `ERROR` from doctor → stop and show it; do not launch. `next-wave` prints one JSON line per ready task (`issue`, `label`, `agent`, `model_hint`, `risk`, `files`). `model_hint` (opus for `risk: high`, sonnet otherwise) is a starting suggestion computed from `Risk` alone, never the decision — see "Model choice" below. Zero ready and some `in progress` → say which are running and stop. Zero ready and zero in progress and not everything Done → the blocked list is a pipeline state, not a business one: read why each task is blocked (`missing` dependency still not `Done`, or `file busy` from a stale worktree) and act on it — resume or relaunch the blocking task per Step 3, fix a wrong `Depends on` in the task file when the block is a planner mistake, run `cleanup-merged.sh` when a `file busy` traces to an abandoned worktree. Notify and skip only the one task whose own note names a genuinely human point (business or product call, money, credentials, an account, a permission, data only the client has, a physical or human check, a production deploy), and continue with the rest of the board.

`dry-run` → print the launch plan and stop.

### 2. Launch — all ready tasks in ONE message
For every JSON line, one Agent call in the same message:
- `subagent_type`: the `agent` field (`developer` or `qa-engineer`) — **never `general-purpose`**: it has no rules, no budget and no read discipline; a task that fits no named agent is a missing agent, not a reason to improvise a prompt
- `model`: your explicit choice for this launch (see "Model choice" below), motivated in one line in the prompt — never just the JSON's `model_hint` forwarded unread
- `isolation`: `worktree` — **only if the session cwd is the project repo** (`git rev-parse --show-toplevel` = the project). From any other folder (the orchestrator running from a hub outside the project) the Agent tool would create a worktree of the wrong repo: instead run `WT=$(bash ~/.claude/agents/pocket-it/bin/worktree.sh <project-path> task/{issue}-{slug})` first, omit `isolation`, and add `Worktree: $WT` to the prompt (the agent `cd`s there; shared rules §5).
- `run_in_background`: `true`
- `description`: `{issue} {label}`
- `prompt`: `Issue: {issue} — {title from tasks/}\nLabel: {label}` plus `Base: {epic branch}` when config `branching` is `epic`.

**Model choice**: yours to make at every launch, not `Risk` alone — `next-wave.sh`'s `model_hint` is a starting suggestion, and the prompt states the reason in one line. Bigger model (opus): irreversible or destructive work, security or permission boundaries, open-ended reasoning (diagnosis, design, root-cause analysis, and their review), a wide surface to keep coherent. Smaller model (sonnet): mechanical, well-specified work, or prose only. The `model` in an agent's frontmatter stays as the floor — no subagent has a default model, so one launched without an explicit model inherits the session's, the most expensive; never omit it. Never change the model as a reaction to a failed round: find the cause first (Step 3), and raise the model only if the analysis itself names the model as the cause.

Then stop and wait for the task notifications. Do not poll, do not read files while waiting.

### 3. Collect
When all notifications are in: list per task the branch, PR and one-line outcome from each report. A task that stopped early (partial / maxTurns / blocker) gets the same cause-first treatment as a red PR (Step 4) — never a bigger model or a fresh run as the first move. Read why it stopped from its own report and place the fix where the cause lives: the task was really two tasks → split it into two Todo files; the input was wrong (a bad `Depends on`, a missing TAD section, a config mismatch) → fix that input and **resume the same agent** with SendMessage; the base moved under it → merge the base into its branch first, then resume; a tool or hook blocked it → fix that in its own lane (the script, the hook, the shared rules), never patched here. Resume on the **same model**, unless the analysis itself names the model as the cause and says so in the resume message. Relaunch from scratch only when the worktree itself no longer exists. Park it (mark the task file `**Status**: Needs Work` with a `Notes:` line naming the cause) only when the analysis concludes the cause is outside what the pipeline can reach — never because the same cause came back once already: a returning cause means the first fix landed in the wrong place, which is a new cause to place correctly, not a reason to stop trying. Only a task whose own blocker is genuinely human — a business or product call, money, credentials, an account, a permission, data only the client has, a physical or human check, a production deploy — is named to the user, and only that one task stops; the rest of the wave continues.

### 4. Review — one reviewer per group of at most 3 PRs, run in parallel
A reviewer runs with `maxTurns: 60`. The measured cost is about 20 turns per PR once a conflict merge or a re-executed mutation check are counted (`shared/lessons.md`, from the same 7-PR stall this rule answers) — not the flat 60/7 ≈ 8.6 turns/PR a wave-size average suggests, which looks like enough right up until the heavier PRs land together. At ~20 turns per PR, 60 / ~20 ≈ 3 is what a reviewer can actually carry before the same limit stalls it again. For a wave of more than 3 PRs, split the task IDs that opened a PR into groups of at most 3 and launch `ceil(n/3)` `reviewer` Agent calls **in the same message**, each `run_in_background: true`, prompt `Tasks: {that group's IDs only}` plus `Draft: yes` when config `automerge` is `false` or the user's request / `$ARGUMENTS` contain `draft`. Wait for all groups. When you already know a PR needs a conflict resolution, weight it as more than one PR when filling a group.

NEEDS WORK items (across every group) → read the cause and its destination straight from the reviewer's Step 6 report line — `cause: {…} — fix at: {…}` — never from the PR comment or the diff, which stay the agents' work; the reviewer's report is also where this cause lives for anyone reading the wave's history back, nothing else needs to carry it. Apply the fix at the place the cause names, before relaunching:
- **example-not-class** (the finding or the task named one or two cases of a class, not the whole set — a guard closed for two command shapes, bypassed by a third): rewrite the acceptance criterion in `tasks/{ID}-*.md` to enumerate the whole class — on the base branch (`git checkout {base} && git pull --ff-only`, edit, commit, push, the same shape used for `tasks/` in Step 5) — and paste the corrected criterion into the developer's relaunch prompt directly, since its branch may not have pulled the base yet.
- **base-moved** (main changed while the PR waited; branch tests stayed green against the old state): the developer's relaunch prompt says, as its first instruction, to merge/rebase onto the current base and rerun the scoped tests before touching anything else.
- **verification-reintroduced** (a report or check written to prove something absent contains that same thing): the fix belongs in `shared/implementing-common.md`'s report-writing rules and in `reviewer.md`'s own check wording — name that as the destination; do not restate the rule's content here as a stand-in for editing those files.
- **other: …**: apply the cause exactly where the reviewer's `fix at:` points.

**When a cause's fix lives in a pocket-it file** (`shared/implementing-common.md`, an agent template, this skill, `verify.sh`, a hook) rather than in the project: that correction goes through a `/quickfix` on pocket-it (mechanism only, no project data) — the orchestrator never edits pocket-it's own files directly. Name it in the report's `Decided on its own` line.

Park a PR only when the analysis concludes its cause is outside what the pipeline can reach — never on a round count, and never because the same cause came back once already (a returning cause means the earlier fix landed in the wrong place, which is a new cause to place correctly, not grounds to stop): `gh pr comment {n} --body "⏸ parked — {reason}"`, `gh label create parked --color eab308 2>/dev/null || true; gh pr edit {n} --add-label parked`, leave the task `Needs Work`, and close the rest of the wave without it.

Then: one developer per PR, in one message, background, prompt `Issue: {id} — {title}\nLabel: {label}\nBranch: {branch} ALREADY EXISTS\nPR: {n}` plus the reviewer's findings verbatim, the cause, and the fix already applied or the instruction to apply it first (per the families above). This prompt — and any later resume prompt to a developer already through more than one review round on the same PR — carries every finding still open across **all** rounds so far, not only this round's, and never narrows scope with language like "no other changes" or "only fix the above": a task once turned four rounds into seven this way, the earlier rounds' findings silently dropped when a later prompt re-stated the scope as just its own round. The report it asks for follows `implementing-common.md` §9 "Resume report format", cited here rather than restated. From a PR's third developer round on, that developer is a fresh launch on the existing branch as above, never a SendMessage resume of the earlier round's agent: the branch, the PR comments and the resume report carry the whole state, while a resumed agent re-reads its whole transcript on every call (measured: eight developers past 300k context in two days, the largest 487k over 705 calls). Step 3's "resume the same agent" stays for an agent that stopped mid-task with work of its own.

**Writing a launch or resume prompt** — the prompt is a specification the agent executes literally, so it obeys the same rules as a task file:
- An invariant is written as the **damage** it prevents, never as the place it was last seen: "no printed command writes to any remote, under any ref name", not "never write to the base" — the place-shaped form was satisfied by a rescue branch that republished the history a deliberate rewrite had removed.
- Never ask for an **outcome** ("bring the check back to green", "make the suite pass") before checking that it can be reached without breaking one of the task's invariants; when it cannot, the invariant wins and the prompt says what the agent does instead ("stays red until a person decides"). An outcome-shaped request produced a command that wrote to the base.
- When **one rule is split across two PRs**, its terms are defined in exactly one of them under a heading, the other cites that heading by name and never restates it, and the merge order follows (definitions first). Two PRs each defining the same terms collided until one cited the other.
- Scope is never narrowed ("no other changes", "only this") — the rule above; a scope check is a verification the reviewer runs, not a limit the prompt sets.
- A task that builds a guard or a check carries its threat model (`implementing-common.md` §9 "Classes of cases and guards"); a prompt that asks to close "every bypass" without one is itself the defect.

Then one more reviewer call per affected group with `Mode: delta` (reads only the fix commits — cheap). **Never merge a PR that carries `needs-work` without that delta re-review**, however small the fix: the reviewer swaps the labels, and a merged PR left with `needs-work` corrupts the retro's numbers.

**Retro trigger — after every review, first round and any delta re-review alike.** `bash ~/.claude/agents/pocket-it/bin/retro-due.sh`. Exit 0 (`retro-due: nothing`) → continue. Exit 2 is a script or environment error, not a "no signals" answer: fix it, do not treat it as nothing. Exit 10 (`RETRO DUE: …`) → first `gh pr list --state open --json headRefName --jq '.[].headRefName' | grep -q '^retro/'`: a match means a retro triggered earlier in this same wave already has a branch or PR open and unmerged — do not launch a second one on the same signals, note it in the report and move on. No match → launch the `retro` agent right now, in background — `subagent_type: retro`, `run_in_background: true`, prompt `Signals:` followed by the script's signal lines verbatim (the exact input `retro.md` declares for this trigger) — never asking, never waiting for the epic to close; this runs in addition to the end-of-board retro in Step 5's "Learning hooks", not instead of it. Run this check once per collect step for the whole wave, not once per review group, even when more than one group's review reported exit 10 at once.

### 4b. Overlay verification — every APPROVED PR of the wave, one tree, before the first merge

Skip entirely when the wave has at most one APPROVED PR: nothing to overlap, no launch, no cost.

Otherwise: launch this here, in the main session — never build or test the tree yourself, you only turn a script's output into calls and this is no different. One Agent call, `subagent_type: reviewer`, `run_in_background: true`, prompt `Mode: overlay\nPRs: {every APPROVED PR's branch, in the order Step 5 will merge them}`. Runs once every group's review is back — every PR of the wave APPROVED or parked — and again from scratch whenever a PR gets new commits after the tree last came back green (a `Mode: delta` landing after a prior overlay pass, for instance) — and always before `gh pr merge` touches any of them. It exists because review runs in groups of at most 3 (Step 4), so two PRs of the same wave sitting in different groups never otherwise land on the same tree until they share the base — exactly the case git's own conflict check cannot see: a shared helper whose signature changed in one PR and is still called the old way in another, a default flipped in one PR that another PR's tests still silently assume, a test that does not even go red but passes vacuously on an empty result. `reviewer.md` Step 3b carries the mechanism (worktree location, remote base, conflict handling, which suite) — this step only says what to do with its answer.

**`RED at PR {branch} — …`** → do not merge any PR of this wave yet. Everything before `{branch}` in the merge order tested green in the overlay tree, so merge those for real now, one by one, the normal way (Step 5's merge command) — this also makes the collision reproducible on `{branch}`'s own side, since its base was stale until this moment. Then relaunch `{branch}`'s developer, cause `base-moved`, first instruction: merge the now-current base and reproduce the failure before touching anything else; findings = the overlay's red output. Then one more reviewer call `Mode: delta` on that PR. Then rebuild — relaunch `Mode: overlay` again, `PRs:` now only the branches still unmerged.

**`BLOCKED at PR {branch} — …`** → the tree could not be built and no test ran on `{branch}`: not a defect of that PR, never relaunch its developer, merge nothing yet. Check the input first: `git ls-remote --heads origin {branch}` returns nothing, or `{branch}` is not the PR's `headRefName` → fix `PRs:` and relaunch `Mode: overlay`. The branch is there → the git lines in the report name a tooling failure (a refused commit, a missing identity, unrelated histories): fix it in its own lane, then relaunch `Mode: overlay`.

**`GREEN`** → proceed to Step 5 and merge the rest normally.

### 5. Close the wave
- APPROVED PRs: merge them, one by one — `POCKET_IT_USER_MERGE=1 gh pr merge {n} --squash --delete-branch` (the hook's authorised form; the prefix is the audit trail that the merge is covered by the `automerge: true` default). After each merge, make sure `tasks/{ID}-*.md` says `**Status**: Done` (set it if the developer left it otherwise, the same check `quickfix/SKILL.md`'s own close step already runs after its merge) — before the commit of `tasks/` below, so a task never reaches the base branch still reading `Todo`/`In Progress`/`Needs Work` under a PR that is already merged (`doctor.sh` also flags this case as a warning, as a net for whoever merges outside this skill). Skip the merge only when config `automerge` is `false` or the user's request / `$ARGUMENTS` contain `draft`: then list the approved PRs for the user, who merges. Never open or merge the epic→main PR of a deployed project here — that is a deploy, done only on explicit instruction.
- `git pull --ff-only` the base branch, then `bash ~/.claude/agents/pocket-it/bin/tasks-index.sh` and `bash ~/.claude/agents/pocket-it/bin/handoff.sh log "wave {n} closed — {merged}/{launched} merged, {approved-draft} awaiting user merge, {needs-work} needs work"`, commit `tasks/` and `docs/` on the base branch, `POCKET_IT_ORCHESTRATOR_PUSH=1 git push` (the hook's authorized form for a push to the base branch, same audit-prefix shape as the merge above).
- Then `bash ~/.claude/agents/pocket-it/bin/cleanup-merged.sh`: removes the worktrees and local branches of the merged PRs (dirty, locked and unmerged ones are kept and listed). Report its summary line (`cleanup-merged: N worktrees removed, … freed X MB`).
- **Learning hooks.** Read the wave's `BUDGET` and `STALL` lines from the handoff log (`grep -E "^- .*(BUDGET|STALL) " docs/SESSION_HANDOFF.md | head`) and list them in the report: they are the raw material of the retro. If `next-wave.sh` now reports everything Done (the board is complete), launch the retro **now**, before reporting: one Agent call `subagent_type: retro`, prompt `{epic id or "board completed {date}"}`, wait, and include its summary — nobody else will launch it once the session closes.
- **Session hygiene.** Compaction is automatic (`autoCompactWindow`): the runtime compacts the session on its own when the context window needs it, without a tool, a hook or a keystroke from anyone. Nothing here waits for it — never hold a wave back, never delay a launch, never end a report with a call to compact before continuing: the work is never suspended waiting for compaction. State is on disk (the board, `docs/SESSION_HANDOFF.md`), so a compaction landing mid-wave loses nothing that matters. Launch the next wave as soon as this one is closed and the user says "vai" (Step 5's own gate below), full stop.
- Report in ≤ 15 lines: launched / merged (or approved, awaiting the user in draft mode) / needs work / blocked, PR links, BUDGET/STALL lines. Add `Decided on its own: {…}` — every cause found and where its fix went, every PR parked and why, every task split, every wrong `Depends on` corrected, every agent resumed and on what basis — the owner sees this every time, even when nothing needed them, because none of it was asked. Then — only if one occurred — the genuinely human blocker named above (business/product call, money, credentials, accounts, permissions, client-only data, a physical/human check, a production deploy) and the one task it stopped. A pipeline snag is fixed above, in the step it belongs to, never carried into this list as a question. Then stop — the next wave is a new `/run-wave`, when the user says "vai" (in draft mode, after the user has merged).
