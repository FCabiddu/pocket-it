# Implementing agents — shared rules

Read once at start by `developer`, `qa-engineer`, `reviewer`. Edit here, never copy into an agent file.

## 1. Project config — never ask, read `.pocket-it.json`

```bash
CFG=$(cat .pocket-it.json 2>/dev/null || echo '{}')
```

| Key | Default | Meaning |
|---|---|---|
| `scope` | `medium` | simple / medium / full — output depth for planning agents |
| `automerge` | `true` | apply the `Auto-merge` label to PRs; the orchestrator merges approved PRs (`false` = review only, the user merges) |
| `pipeline` | `false` | hosted CI/CD wanted (GitHub Actions + `APP_STATUS`) |
| `baseBranch` | `main` | branch tasks fork from and PRs target (an epic branch if `branching: epic`) |
| `branching` | `flat` | `flat` = task branches off `baseBranch`; `epic` = `epic/...` branches, orchestrator passes `Base:` |
| `testCommand` | auto | project's affected-tests entry point, e.g. `pnpm test:affected` |
| `tests` | `{unit: required, integration: on-demand, e2e: on-demand}` | test policy — see §4 |
| `ticketPrefix` | `T` | task id prefix used by the board |

Rules: a value passed in your arguments (`Base:`, `Label:`, `PR:`) wins over the file; the file wins over the default. If you run in an isolated worktree (`pwd` contains `/.claude/worktrees/` or `/.worktrees/`) you see only **committed** files: a missing `.pocket-it.json`, `tasks/` or TAD there means the orchestrator did not commit them — report that in one line and stop, do not go looking elsewhere. **Never call `AskUserQuestion`**: you run as a subagent and the call fails. If something is genuinely blocking, stop, state the assumption you would need, and report. Missing file = defaults, say so in the report.

## 2. Local board — `tasks/`

One file per task, `tasks/{ID}-{slug}.md`. Header fields are `**Key**: value` (tolerate `**Key:** value` in older projects). Canonical statuses: `Todo`, `In Progress`, `Done`, `Needs Work`.

```bash
TASK_FILE=$(ls ./tasks/{ID}-*.md 2>/dev/null | head -1)
set_status() { sed -i.bak -E "s/^\*\*Status\*\*:.*|^\*\*Status:\*\*.*/**Status**: $1/" "$TASK_FILE" && rm -f "$TASK_FILE.bak"; }
set_field()  { grep -qE "^\*\*$1(\*\*:|:\*\*)" "$TASK_FILE" && sed -i.bak -E "s#^\*\*$1(\*\*:|:\*\*).*#**$1**: $2#" "$TASK_FILE" || printf '**%s**: %s\n' "$1" "$2" >> "$TASK_FILE"; rm -f "$TASK_FILE.bak"; }
```

Use `set_status "In Progress"` before code, `set_status Done` after checks pass, `set_field PR "$PR_URL"`, `set_field Branch "$BRANCH"`. Never edit `tasks/INDEX.md` by hand — it is regenerated with `bash ~/.claude/agents/pocket-it/bin/tasks-index.sh` by whoever needs it up to date (planner, reviewer, orchestrator).

## 3. Read discipline — the cost is what you read back

- **Zeroth, the method lessons:** `~/.claude/agents/pocket-it/.claude/agents/shared/lessons.md` (one-line lessons of at most 300 bytes each, stack-independent, written by the retro across projects — what is still being learned; what held is already a rule in the files below). They apply to you whatever the project; a `provisional` one is still followed.
- **You read that file; you do not add to it when you close a defect.** The rule goes where agents read it at start — a section of this file, the agent's own template, the project's `best-practices/` — and writing it there **is** the promotion: nothing further is owed, and a `lessons.md` line repeating it is a copy re-read on every launch, which that file's own header deletes on sight. A lesson is only for a rule whose destination is **not yet decided or not yet reachable**; when that is your case, put the line in your report and leave the file to `retro`. One fix round wrote its rule into a start-read file *and* a copy here, and cost a whole extra round spent deleting the copy.
- **First, the facts other agents paid for.** `bash ~/.claude/agents/pocket-it/bin/handoff.sh facts 2>/dev/null` — the whole facts section, up to the cap of 100 one-line facts, composed from the project's memory (PI-14/PI-15) whatever it is made of today: invariants, gotchas and decisions written by previous agents (a `cache()` that is a pass-through in tests, a route that must be listed in a census test, a token that must not be redefined). Reading them is how the pipeline learns; if one of them is wrong today, fix it with `handoff.sh fact` and say so in the report.
- **A wrong value in a file agents read at start is corrected in every file that states it, not only in the one you found it in.** Defaults, units, budget tables and environment facts are each written in several of these files — this one, the agent templates, the skills that emit a task file — so a correction landed in one leaves the others emitting the old value to every agent launched after it: a budget table moved to minutes in two files and left in turns in a third went on producing unitless task files for days, and a disproved environment fact came back in an agent report the same day it was fixed elsewhere. `git grep` the old value, fix every hit or say why a hit is correct, and put the count in the report — a correction whose reach you did not measure is a correction in one place.
- Read the task file, then only the TAD sections it references. Extract a section by number, never the whole document:
  `awk '/^## 5\. /,/^## 6\. /' tech-analysis/X_TECH_ANALYSIS.md`
  When the task cites `PROJECT §… · DELTA §…`, the delta (`tech-analysis/{NAME}_TECH_DELTA.md`) overrides the project TAD (`tech-analysis/PROJECT_TECH_ANALYSIS.md`) for those sections.
- If the task cites a `**Contract**:` file, read it in full: it is the agreed API shape between backend and frontend and it is not yours to change without saying so in the PR.
- Do not read the IPD. The task file is self-contained; if it is not, that is a planner bug to report, not a reason to read 800 lines.
- Read a source file **once**. After an `Edit`, do not re-`Read` the whole file; the Edit result already confirmed the change. Re-read a range only when you need lines you have not seen.
- Cap command output: `| head -60`, `--reporter=dot`, `--silent=passed-only`, `2>&1 | tail -40` on compilers. Never dump a whole log.
- Best-practices files: `find . -type d -name best-practices | head -1`, then read only the file(s) for your label. Binding, not advisory — if the task cannot be done without violating one, stop and report the conflict; do not decide alone.

## 4. Tests — unit done well by default, the rest only when it earns its place

**Default policy (overridable per project in `.pocket-it.json` → `tests`):**

| Layer | Default | Who | When |
|---|---|---|---|
| Unit + component | `required` | developer, in the same PR as the code | every task that adds or changes behaviour |
| Integration (a real disposable DB, §9 / real API) | `on-demand` | qa-engineer, as its own QA task | only when the planner justified it: money, auth, data integrity, a contract several clients depend on, or a bug that unit tests could not have caught |
| E2E (browser) | `on-demand` | qa-engineer, as its own QA task | only the 1–3 journeys the product cannot ship broken (checkout, login, the core flow) — never one per screen |
| Accessibility | `required` (floor) | developer (axe on the component), qa if E2E exists | every frontend task |

"Done well" for unit tests means: one behaviour per test named as scenario + outcome; happy path, the edge cases the acceptance criteria imply, and the error paths; behaviour, not implementation; deterministic, independent, factories over inline literals; coverage of the code you wrote, not of the repo. A task whose "Tests expected" section is empty and that changes behaviour is a planner defect — write the tests anyway and say so. A test that asserts an absence (no error, no match, no duplicate) has a sibling test whose input does contain the thing and asserts it is found; run that sibling once with the reading step broken (wrong path, empty input) and see it go red before trusting the absence test — an input never read passes the absence test the same way a clean one does.

**A test offered as proof that a criterion holds is run once with the behaviour it asserts broken — the mutation — and that red output is pasted in the PR.** This is the whole difference between a test and a green light: a test whose mutation stays green proves nothing, whatever it is named and however many assertions it carries. One epic shipped five green suites over broken code this way — a matcher that ignored the very attribute it was asserting, a stand-in that does not implement the behaviour under test, six state attributes nailed to a constant under 213 green tests, a deduplication deleted at its call site with all seven of its unit tests still green. Mutate what the criterion is about (the value, the branch, the guard), not a neighbouring line; if no mutation can turn the test red, the test is not evidence and the PR says so instead of citing it.

`tests.integration` / `tests.e2e` values: `off` (never, even if asked by a task — report instead), `on-demand` (default), `on` (the planner adds a QA task per story). Unit tests cannot be turned off.

**Which tests to run** — the dependency graph, never the whole suite. Resolution order, stop at the first hit: (1) `testCommand` from config or a `test:affected` script in `package.json`; (2) the runner's own selector on the files git says you changed — `vitest related --run <files>`, `jest --findRelatedTests <files>`, `pytest <module>`, `go test ./pkg/...`, `cargo test -p <crate>`; (3) naming convention, and say in the report that scope was heuristic. Changed files, against the remote base — §6 branches from `origin/$BASE`, not a local checkout of it, so compare against the same ref or the list widens or empties depending on how stale the local one is:

```bash
git diff --name-only $(git merge-base "origin/$BASE" HEAD) HEAD; git status --porcelain --untracked-files=all
```

**Run every check in the foreground, never in the background, and never wrapped in a command that may not exist on this host.** `timeout` is absent on macOS and `gtimeout` is only there when coreutils was installed: a command wrapped in a missing binary does not run at all, and the agent then reports on a run that never happened. A suite left in the background is worse: the agent has nothing to wait on and idles — one review lost 31 minutes that way, on a machine where the full suite was itself measured at 31 minutes. So: the scoped run in the foreground, and if a bound is genuinely needed, one that exists everywhere — the runner's own (`--testTimeout`, `-timeout`) or `perl -e 'alarm N; exec @ARGV' -- <command>`. Waiting for something you did start in the background is a bounded `until` loop on a condition (§5), never `sleep`.

Full suite at most once, as the gate before the PR, and not at all if hosted CI runs it. Integration (a real disposable DB, §9) and browser E2E only if the change touches their surface. Type-check is project-wide by nature; run it after a batch of edits, not after every edit — three consecutive failing type-check rounds on the same error means stop, re-read the error, and change approach.

## 5. Shared machine and worktrees

Other agents and the user's app share this machine. Never `pkill`/`killall` (a hook blocks them anyway): stop your own process by PID or by the port you chose (`lsof -nP -iTCP:3100 -sTCP:LISTEN -t | xargs -r kill`). **Port 3000 is the user's, and the way to not take it is to never start a server with its default command**: `npm run dev`, `vite`, `rails s` and their kind all grab it. Pass the port explicitly every time (`-p 3100`, and 3100 + the task number when several agents run), pass that same port to whatever drives the browser, and stop the server on the port you chose. A default command that took 3000 for a minute is still a breach: free it and say so in the report. Never use `sleep N && …` to wait — it is blocked; use `gh pr checks N --watch` or a bounded `until` loop. Admit any breach in the report.

**Worktree handed to you.** If your arguments carry `Worktree: <path>` (the orchestrator created it with `bin/worktree.sh` because its session runs from another folder), `cd` there first and stay there: you are already on your branch, never run `git checkout <base>`.

**Worktree gone — stop, never fall back.** Applies whenever you work in a worktree (`Worktree:` given, `isolation: worktree`, or `pwd` under `/.claude/worktrees/` or `/.worktrees/`). The shell's working directory resets between commands to where the session started — usually the project's main checkout — and a worktree can vanish under a running agent (a cleanup after someone else's merge, a manual prune). So:

1. **First command:** `cd '<Worktree: path, if given>' && git rev-parse --show-toplevel`; note the output as `WT`. If it is the project's main checkout although you were meant to be in a worktree, stop here.
2. **Every shell command starts with `cd '<WT>' && …`** — `&&`, never `;`, so nothing runs when the path is gone. `<WT>` is the **literal path text**, written out in full in each command: never a shell variable (`cd "$WT"`), never `~`, never a value computed by another command. The harness decides whether a command may touch git by reading the command's text; a directory it cannot resolve by reading makes the whole command unverifiable and it is refused, costing a turn and changing nothing. The same reading is why `git`/`gh` calls go one per command: a `for` loop, a `;`-chain or a subshell around them is refused as "too complex to verify", and a one-off read of another repo is `git -C '<literal path>' …` rather than a `cd`. Isolation blocks are the largest single failure signature in the usage report (121 in one two-day window; 3 in a single 60-turn run, all from a loop or a variable-named directory).
3. **Once, when the branch is yours:** right after §6 creates or checks out your branch — or in the first command, when it was already checked out for you (`Worktree:` given) — note `git branch --show-current` as `BR`.
4. **Every commit carries the branch check:** `cd '<WT>' && [ "$(git branch --show-current)" = '<BR>' ] && git commit …`. Nothing is checked before a file edit: an edit on a vanished path fails by itself, and the next shell command or commit catches the loss before anything is committed.
5. **When a `cd '<WT>'` fails, the branch check fails, or a file tool reports that a path under `<WT>` no longer exists: stop and report** — `WT`, `BR`, the last commit you pushed, what was left uncommitted. Do not recreate the worktree, do not check the branch out elsewhere, and **do not continue in the main checkout or in any other directory** — not for a one-line edit, not for a test run, not for `handoff.sh`. A change made there lands in the tree every other session and every hook reads, with no branch, no review and no PR; lost uncommitted work is recoverable, an unreviewed edit to the shared tree may not be noticed at all. Commit early: uncommitted work is exactly what a vanished worktree takes with it.

**Paths in a worktree.** `<WT>` is the only tree you may touch. Shell commands, after their `cd '<WT>'`, use paths **relative to it** (`tasks/…`, `src/…`, `docs/…`); file tools (`Read`, `Edit`, `Write`) accept only absolute paths, so they get `<WT>/…` and nothing else. Never a path into the project's main checkout (`…/<project>/src/…`) or another worktree (`…/.worktrees/other/…`), never `cd` into another checkout, never `git -C <other path>`. The harness blocks such commands and each block costs a turn; in the 2026-09-06 session it cost 34. If a task file or the orchestrator hands you an absolute path, strip it to the repo-relative part.

## 6. Branch, commit, PR

```bash
BASE={Base: from args, else baseBranch}
git fetch origin
git checkout --no-track -b {branch} "origin/$BASE"   # or: git checkout {branch} && git pull origin {branch}  if "ALREADY EXISTS"
```

Branch straight from `origin/$BASE`: no local checkout of the base, which a worktree cannot do while the base is checked out elsewhere. Skip the block when `Worktree:` was given — you are already on your branch. Right after it, note `BR` (§5, step 3).

Commit early and often (a killed agent loses uncommitted work). Before `git add -A`, check `git status --short` for `.env`/credentials and gitignore them. Commit trailer: `Co-Authored-By: Claude <noreply@anthropic.com>`. Push, then open a **draft** PR against `$BASE` with `gh pr create --draft --base "$BASE" …`. Never `gh pr merge` (the orchestrator merges after the review), never push to `main` directly (hooks block both). If `automerge` is true: `gh label create Auto-merge --color 94a3b8 2>/dev/null || true; gh pr edit $PR_NUM --add-label Auto-merge`. **The PR body's Changes section lists every file the diff touches, housekeeping included** — the task file, the report, the handoff fragment, a regenerated index. They are required by these rules, so they are never a surprise, but a body that says "nothing outside `**Files**`" while the diff carries them is simply false, and the reviewer who spots one has to re-verify every other claim in the body. Check the sentence you are about to write against `git diff --name-only $(git merge-base "origin/$BASE" HEAD) HEAD` before writing it. Record `$PR_URL` in the task file. Then log the event — this is the project's memory across sessions, and it is mandatory:

```bash
bash ~/.claude/agents/pocket-it/bin/handoff.sh log "{ID} PR #{n} draft — {what, six words} — {tests added}"
```

**`handoff.sh` writes into the tree you are standing in, and a line written where nothing is ever merged is a line lost.** Before you run it, know which of the three cases you are in: (1) a worktree whose branch becomes a PR — read the next paragraph before writing anything, because most of the time the answer there is not to write it on your branch at all; (2) the project's main checkout — write it normally; (3) a **throwaway worktree** (a review scratch, `verify.sh`'s, an overlay) — nothing there is ever merged, so **do not run `handoff.sh` there at all**: put the line you would have written, verbatim and in its exact shape, in your report under a `## Handoff` heading, and say in your return that it still has to be written on the base branch. One review's log line landed on a scratch branch that nobody merges and survived only because its author noticed and said so. A branch nothing merges is case (3), whatever it is named.

**The question is never who merges your branch; it is how many branches write that memory in this window.** "This PR merges it" is a true answer that still produced a corrupt file: it authorised a hand-written entry on every branch of a wave, and those entries did not conflict cleanly — one such file ended up hiding 26 log lines behind a duplicated section heading while still reading plausibly, after a day of chained conflicts and a hand reconciliation that moved facts out of the section agents read at start. The fragments of the next paragraph remove exactly one half of that: a write **made with the tool** now creates a new file instead of editing a shared one, so parallel branches merge as a union — 0 conflicts across four branches, one of them squash-merged, is a criterion `bin/handoff.test.sh` proves, not a hope. They remove nothing of the other half: a line typed in by hand, a file reconciled by hand, a rotation by size corrupt the memory exactly as before, whatever the tool does. So the instruction does not change: whenever more than one branch is open on the project — a wave, a review group, any parallel lane — **every write stays off the feature branches**: put the line in your report under a `## Handoff` heading, verbatim and in command form (`handoff.sh log "…"`), and one step on the base branch replays it **with the tool** — never by hand, never reconciled by hand, never rotated by size — then re-runs a structural check over the whole memory (one heading per section, no undated line in the log, no count lower than the base; §9, a repair is verified over the whole artefact). Only when you are genuinely the single branch writing in this window does case (1) stand: write it with the tool and commit the fragment it creates in your PR. `tasks/PI-52` is **not built yet**: nothing refuses the write for you today, so this paragraph is the whole of the guard — when that task merges it will move this from discipline to a refusal in `handoff.sh` itself.

**Every write creates one new file** under `docs/handoff/{AAAA-MM}/` and never reopens an existing one — `handoff.sh where` prints the directory it would use, from any folder, without writing anything — so two branches writing memory at the same time merge as a union and nothing has to be resolved by hand. `docs/SESSION_HANDOFF.md` and `docs/SESSION_HANDOFF_ARCHIVE.md`, where the memory used to be kept, are frozen sources: still read for ever, never written again. Nothing is ever dropped either: the 40 is only how many log lines `show` displays. Use `handoff.sh fact "…"` **only** for something the next agent would otherwise rediscover the hard way (an invariant, a gotcha, a decision and its why) — never for progress. **And only for what a command actually showed you.** The handoff is read as fact by every later agent, so an inference written there becomes a false premise nobody re-checks: three lines describing an environment — a production deployment, migrations waiting to be applied, a hosting provider — were each written from what seemed obvious, none of the three existed, and a separate PR was needed to take them back. Put the command and its result in the line itself; if you did not run one, either do not write the line or mark it `ipotesi, non verificata` in the line's own words. This binds whoever writes the handoff, the orchestrator included. When the paragraph above leaves the write to you — case (1), genuinely the single branch writing in this window, or the base branch itself — commit the fragment with your task file (`git add docs/handoff`); otherwise nothing under `docs/handoff/` belongs in your diff and the line travels in your report instead.

**CI-fix mode** (`CI Failure:` in arguments): do not touch task status, do not open a new PR; commit on the existing branch and `gh pr comment $PR "🔧 CI fix — {what}"`.

## 7. Report — the long version on disk, eight lines back

The orchestrator's context is the most expensive thing in the pipeline, so what you return is short and what you write down is complete. Before your final message, write `docs/reports/{ID}-{YYYY-MM-DD}.md` (≤ 40 lines: what changed and why, tests ↔ criteria, deviations, checks run with their result, the `Effort:` line, anything the next agent needs) and commit it with your task file so it travels in the PR. **Effort is reported in one unit and one line: elapsed wall-clock minutes.** You cannot count your own turns — you have no counter — so any turn figure you write is invented, and a rule that asks for one gets a different substitute from every agent: within hours of such a rule three reports came back reading "Turns: 290 s / 3 commits", "Elapsed 554s (~9,2 min) · 4 commits" and "~31 turns". None of the three was dishonest and no two were comparable, which is the whole defect. So there is exactly one effort number, in minutes, in this shape:

```
Effort: 23 min elapsed (budget 90 min) — wt:agent-acee2c67
Effort: 31 min elapsed (budget 45 min) — wt:task-pi-36-guard-force-push-boundary
```

`date +%s` in your **first** command and again in your **last**, difference divided by 60, **rounded to a whole minute**. Wall clock, waiting included; that is what it is, and it is the same for everyone. The budget in brackets is the task's, in minutes (§8). `wt:` is the **basename of your working directory**, from `basename "$PWD"`, copied out exactly as it comes — nothing prefixed, nothing interpreted. Both shapes above are correct: you get `agent-<hex>` when you were launched with `isolation: worktree`, and a branch slug when you were given an explicit `Worktree:` path, because `bin/worktree.sh` names that directory after the branch (`SLUG="${BRANCH//\//-}"`). Which shape you get is itself the information — it tells the retro how you were launched — so a slug is never something to dress up as an id.

**It is not your agent id, and you must never write one there.** No agent can read its own id from inside its run: it is assigned by whoever launches you and appears in no file and no variable you can reach (`CLAUDE_CODE_SESSION_ID` is a session UUID, a different thing). Nor is it wanted from you: `usage-report.py` takes the real id from the **launching session's** transcript (`bin/usage-report.py:59`, `agentId:` in the Agent tool result) and never opens `docs/reports/` at all. Wrong, both from real reports the day this field was introduced, each wrong in the way its launch invited: `— agent-task-pi-36-guard-force-push-boundary` (a branch slug turned into a fake id by the `agent-` prefix) and `— agent-a200fa577c0bfe3d3` (a real id — belonging to a *different* agent, which had just finished). The minutes in both were correct; only the invented key was wrong. **A fabricated identifier is worse than an absent one, because it reads as evidence.**

Wrong, all three from real reports: `Turns: 290 s / 3 commits` (seconds, and a second quantity nobody asked for) · `Elapsed 554s (~9,2 min) · 4 commits` (seconds plus a tilde) · `~31 turns` (a unit you cannot measure, and a tilde on a number declared as counted). A number carrying `~`, "about", "roughly" or a range **is an estimate**, whatever the sentence around it claims.

**When the number is not available, say so — never substitute another quantity in silence.** If you did not take the starting timestamp, the line is exactly `Effort: not available — no start timestamp — wt:{basename}`: the working directory's name is readable even when the clock was not taken. Seconds, commits, tool calls and "it felt like" are not fallbacks for minutes: a missing number costs the retro one data point, a silently swapped unit costs it the comparison across every report in the window. Commits belong to the Changes section, not here.

**A list or a classification handed over as evidence of completeness carries, for every row, the command that produced it or excluded it.** An exclusion is an assertion: a row excluded by reasoning counts as **not looked at**, and a justification in place of a measurement is a defect even when the conclusion turns out to be right. Mark each row ran or read, and run the ones where the invariant's own nouns change kind — 3 of 43 rows filed as handled routed through nothing. **A census that states a total accounts for every unit of that total.** "Everything else is X, Y or Z" is not a bucket: replace the catch-all with one named row and its own count, so the rows sum to the total you declared and the reader can check the arithmetic instead of trusting it. An enumeration that closed that way left 6 of a declared 78 lines in no bucket at all — one of them the most load-bearing site in the census, and the only reason it cost nothing is that someone else re-derived the conclusion by hand. The sum is the check, and it lives in the artefact rather than in your word for it: rows that do not add up to the stated total are incomplete evidence, whatever the conclusion says.

Then return **at most 8 lines**: ID and status · branch and PR URL · tests added and scoped-run result · the `Effort:` line and whether `BUDGET`/`STALL` was logged · blockers or deviations in one line · `Report: docs/reports/{ID}-{date}.md`. No prose, no explanations — they are in the file.

## 7b. Write only what belongs to the repo you are in

Every repo you may be launched in falls into one of two kinds, and what you may write down differs.

**A project repo** (the usual case): write freely about that project. Its own names, paths, ids and code are what the task is about.

**This tooling repo** (`pocket-it`): **nothing from any project it works on may appear here — ever, relevant or not.** It is public and the projects are not. Not the project's name, not its product or domain vocabulary, not its file paths, not its PR or issue numbers, not excerpts of its code, documents or data, not a narration of the session it came from. This binds every artefact you produce: the task file, the report, commit messages, the PR title and body, `shared/lessons.md`, the handoff memory (`docs/handoff/**`).

A tooling bug is almost always found while working on a project. Describe it by its **mechanism** only: the line that breaks, the shape of input that triggers it, the expected behaviour, how to reproduce it from nothing. If you cannot write the diagnosis without naming a project, the diagnosis belongs in that project's report and only the mechanism comes here.

The id shapes this repo defines itself — `T-{e}.{s}.{t}`, `T-BUG-{n}`, `QF-{n}`, `PI-{n}` — are its own conventions, not project data: they stay usable as examples and as test fixtures.

The same care applies to what reaches you: a launch prompt may carry project context because whoever wrote it had that context in mind. Strip it. Nothing obliges you to repeat it, and being told it is not permission to write it down.

## 8. Budget and stop conditions — stop on stall, not on size

Every task carries `**Budget**: N` **minutes** of wall clock, set by the planner from its estimate (XS 45 · S 90 · M 150 · L 240, or a custom value for work that cannot be split, e.g. "run the whole suite and fix the reds"). Missing → assume 90. Minutes, not turns, because minutes are the one thing you can measure about yourself (§7); the sizes above are the old turn budgets converted at the rate measured over the pipeline's own transcripts (median 47 s per turn, 2026-09-15). A task file still written in turns is read at that rate and the report says so in one word. **A `Budget` whose value carries no unit is a turn-era file** — read it at that rate, name the conversion in the report's budget bracket, and never take the bare number for minutes: the same bare `200` was read as 157 min by one agent and as 200 min by another, and the second reading turned a 60 % overrun into a report that declared itself within budget. A comparison whose two sides are in different units is not a near miss, it is a green that means nothing. The budget is an **expectation, not a wall**: it is there so that a task that costs twice its budget teaches the planner to estimate better, not to interrupt you while you are getting things done.

Two different signals, two different actions:

- **Budget exceeded while progressing** (commits landing, tests turning green): keep going. Log once — `bash ~/.claude/agents/pocket-it/bin/handoff.sh log "BUDGET {ID} {elapsed} min elapsed vs budget {budget} min — wt:{basename} — progressing: {tests} tests green — {why bigger than estimated}"` — and finish. The retro reads these lines to correct the estimates.
- **Stall**: **20 minutes** of wall clock with no new commit and no additional passing test, or the same error surviving three fix attempts. Both are things you can check: the clock, and your own count of attempts on one error. Stop: commit what is coherent, push, log `handoff.sh log "STALL {ID} {elapsed} min elapsed — wt:{basename} — {what is stuck, one line}"` and report. A clean partial report is cheaper than a runaway.

Also stop, with the branch pushed, when the task needs a decision only the user can make, a best-practice conflict appears, or the scope turns out to be several tasks (say which). The agent's `maxTurns` (300) is a safety net far above any budget, never the plan; if you hit it, something above already went wrong.

## 9. Rules from real incidents

### Database terms — real, shared, disposable

**Shared** is any database that this run did not create, that is still there when this run ends, or that anything outside this run actually reads or writes while you use it — a person, another agent, another run, or a program that neither you nor a process you started launched. Whatever only carries this run's own reads and writes — the database server or engine that hosts it (already running or started by you, in a container or not), the container runtime, a connection pooler or proxy, the operating system — is part of the path to the database, not something outside this run. Shared examples: an already-running server's own databases, the persistent development database, a staging or production instance, a database a config file points at that you did not create yourself, a container or a file you leave behind for the next run. That something else *could* open it — a port on this machine, a file in a temporary directory — does not make it shared; something outside this run opening it does. **Disposable** is every other database, without exception — exactly the ones this run created, removed before it ends, and nothing outside this run read or wrote in between: a container you start and remove, a file you create and delete, a database you `createdb` and `dropdb`, an in-memory database (a real engine's own in-memory mode, or a stand-in such as pg-mem, H2 or any other fake) that exists only for the process you started — even when a config file such as `.env.test` or a test compose file points at it. Who created it, whether it is gone before this run ends, and whether anything outside this run actually read or wrote it meanwhile decide — those three and nothing else; a config file never does, the engine never does, and the server that hosts it never does. **Real** is a separate axis, engine not lifecycle: the project's own database engine running real queries — Postgres, MySQL, SQLite, on disk or in the engine's own in-memory mode — never a mock, a stub or a stand-in engine (pg-mem, H2, any other fake) standing in for it. Real decides whether a `real DB` requirement is satisfied; it never decides whether you may write — a disposable mock is as writable as a disposable Postgres container, and a real engine does not make a shared instance safe to write to. *This run* is your agent run, from launch to your final report. Every `real DB` / `live DB` mention elsewhere in this file, and every disposable database asked for as proof — an integration test, a migration or a backfill, a query or migration a reviewer's correction is run against — means *real-and-disposable*: a genuine engine created for the run, isolated per rollback/truncate, never the shared one; that is also what `qa-engineer.md`'s integration tests run against. **Realistic data**, for whoever verifies a fix, means realistic rows seeded on a disposable database — never a write, rolled back or not, to a shared one (rules below). If a task needs a `real` disposable database and you cannot create one here (no container runtime, the project only configures a shared instance) — a mock does not satisfy that requirement, and the shared instance is never a substitute for it: stop, push what you have, and report `blocked — no disposable real database: {why}` (§8).

As a check, not a rule of its own: an in-memory SQLite database your test runner opens is disposable, whatever `real` says about it; pg-mem or H2 standing in for Postgres is disposable and not real — it was never shared, so the rules below never reached it anyway. A container this run starts and leaves running is shared, because it is not gone before the run ends; the same container stopped and removed before you finish is disposable. A database you `createdb` on an already-running server and `dropdb` before you finish is disposable — that server hosts it, it does not read it from outside this run — unless another run connects to it meanwhile; every other database on that server stays shared. An existing staging database is shared, and restoring a dump over it is a write to a shared database. A test database a config file points at that you did not create is shared; one you create and remove yourself is disposable regardless of what the config says. A SQLite file your test creates in a temporary directory and deletes before the run ends is disposable, although any other process could have opened it; the same file opened meanwhile by another agent's run is shared.

- **A check that a string is absent never writes that string into anything committed or published** — report, commit message, PR title/body/comment, handoff, or test fixture. Put the pattern in a file outside the repo and run `git grep -c -f <that file>`; write only the effect in the report ("0 occurrences of the removed name across the tree"). Repeating the string anywhere committed republishes what the check proves removed.
- **A migration or a backfill is never applied to a shared database before review and merge.** Prove it on a real disposable one; state the exact command and the target database under the PR's **Manual setup steps**, and add `after merge: apply {migration} to {database}` to your 8-line return — whoever merges cannot read the diff for it.
- **No write to a shared database, ever — insert, delete, truncate, a rolled-back transaction, none of it: not to try something out and not during review.** A transaction you intend to undo is still a write attempted on data other people depend on right now; use a disposable database instead.

### Classes of cases and guards

- **Test a class by construction, never by sample.** When the behaviour is defined by a declaration — a list of aliases, an argument grammar per subcommand, the id shapes a regex accepts, the categories a definition partitions, the commands a script prints — the test iterates that same declaration or executes the real output (every printed command, run as printed, on names holding `( ) $ ' " ; | &` and spaces), so a new entry is covered the moment it is declared. When the task or a finding gives only examples, name the class's dimensions yourself, put the table of cases in the report, and cover all of it: the rounds that closed only the examples shown came back, 16 times in two days.
- **A test takes its case list from the declaration and its expected values from somewhere else.** Deriving the whole test from the code under test buys coverage and proves nothing: a table-driven test that iterated every declared entry compared each result with the very function it was testing, so a wrong rule in that function was green by construction and shipped. The oracle — what the answer *should* be — comes from outside the implementation: the spec, the standard, the source document with the page cited, a table written by hand, a second independent computation. If no independent oracle can be written, say that in the PR instead of calling a self-comparison a proof; either way §4's mutation rule applies.
- **When the oracle is an external document — a spec, a standard, a rulebook, a PDF — extract it with a tool, never by reading and retyping.** Run the format's own extraction command (`pdftotext -layout` for a PDF, the format's own parser otherwise), cite that exact command plus the page or section in the PR body; §4's mutation rule still applies. A value copied out by eye is not independent of the person who also writes the fix: the same misreading lands in both, because both come from one read of the same page by one person. Mechanical extraction plus a per-entry hand check against that extracted text is; a hand-transcribed table read from memory is not, however carefully it cites its source.
- **A list handed to you — in the task, in a finding, in a prompt — is an input, not the class.** Before anchoring anything to it, regenerate it from whatever produces those values (the real log, the real board, the declaration, the command's own output) and compare: one round was spent because a reviewer hand-copied six real forms out of a file that contained seven, and the developer anchored a parser exactly to the six. What converged was a test that rebuilds the list from the producer at run time, so the seventh form is covered the day it appears. When the list you were given turns out to be short, say so and cover what you found.
- **A structural guard scans the branch, not the directory it is running in.** "Exactly one definition of X in the whole repo", "no file still says Y" and every other repo-wide `grep -r` must take its file list from what the branch tracks (`git ls-files`, or an explicit exclusion of the worktree root) — never from walking the checkout. Sibling branches are checked out *inside* the repo while a wave runs, so a tree walk reads their files as if they were this branch's: three such guards exist with `--exclude-dir=.git` and nothing else, and one of them is red right now against a correct branch because a parked worktree still holds a pre-migration copy of the file the guard counts (`tasks/PI-61`). The damage is not the red itself but where it points: it names a source file this change never touched, and the next agent is invited to "fix" it — see *Reds you did not cause* below, which is the only thing standing between that guard and a wrong edit.
- **Every guard or check states its threat model at its top** — the comment heading the code, or the opening sentence of the doc section: what it protects against and what it deliberately leaves to another layer (server-side protection, a person). A bypass outside that model is noted under "not covered", not chased; one inside it is a defect. A guard without a stated model grows a new bypass every round: one reframed in its second round closed in four, one never framed was cancelled after three.
- **A self-mutating fixture edits a copy under the suite's own temp directory, never the checked-out file itself — not even briefly, not even behind a `trap … EXIT` restore.** A trap protects the process's own exit path; it does nothing for a concurrent reader — a `git commit`, a second test run, an editor's autosave, another agent — that opens the file during the window it is mutated, before the trap fires. If a fixture must run the tool against edited source text, build the edit into a copy (a `mktemp` file or directory) and point the invocation at that copy; the real path on disk stays byte-identical to `HEAD` for the whole run, provably (a background reader sampling it for the run's duration, not an argument that no window exists). A duplicated function landed inside a real git commit this way: the recursion in `bin/doctor.test.sh` mutated `bin/doctor.sh` in place and relied on restore-after-each-case to put it back (PI-63).

### Reds you did not cause, absences you did not measure, repairs you did not re-check

- **A check that goes red on code this change never touched is diagnosed before it is fixed, and never fixed in the source it points at.** Look at the environment and the base first: the installed tree against the lockfile, a clean reinstall, or that same check re-run against a clean checkout of the base branch's own tip. A check that fails there too is inherited, not introduced — report it, never charge it to this change and never label it your own rework; one mismatched install sent three agents to change source that was already correct, and the change would have broken the build once the dependencies were right. The drift also runs the other way and shows no red at all: after any merge that touches a lockfile, reinstall the shared checkout before trusting a green — two days of green runs once stood on a dependency version the lockfile no longer declared, caught only when someone's own throwaway clean install disagreed with the shared one (`tasks/PI-51` moves this from habit to a gate).
- **A claim a command could settle is run before it is written down, and the command is named beside it.** This binds every assertion of fact you hand over, not only the conclusion that there is nothing to change: the state of another task, branch or PR ("merged", "done", "already landed"), what a piece of code does, what a mutation removes, a number, a size, a coverage. "No gain", "already handled", "already correct", "already covered", "within budget" are claims about an effect, so measure the effect where it is expected **and at every site the claim covers**; produce every number with the tool that owns it, from the main checkout, and name that tool — a `grep` standing in for the runner once counted 25016 files against 229. Write into a report, a code comment, a PR body or shared memory only what was measured. A size task that measured the one page where no gain was possible called the gain nil and wrote that into the project's facts; the other page had moved 6 %. "The rest were already correct", written over 43 classified sites of one script, was false at three of them — found by running 3 rows of that table instead of reading them. **An unexecuted claim keeps travelling until someone runs something**, and a correction derived the same way inherits the defect: a sentence about what a text transformation removes was derived by reading it, found wrong, rewritten twice — each rewrite also derived by reading — and each was wrong about the same mechanism. Reading a rule and concluding that the mechanism it describes exists is the same defect: **a task id or a PR number is a state you check on the board, never one you infer from the prose that cites it** (two tasks are open, neither built yet: `tasks/PI-59` would turn that check into a refusal, `tasks/PI-55` would reword the prose that invites the inference — until they are `Done`, this rule is all there is). The PR body is the most expensive place for a false claim — it becomes the squash-merge commit message on the base branch and stays there for good.
- **A repair is verified over the whole artefact, never over the line it touched.** A correction carries the defect it is correcting more often than anyone expects, so before declaring a repair done re-run the structural check over the entire file, rule or document — not over the field you edited. A restored section heading was put back above twelve entries instead of moving them out first, declared fixed without the one-line structural check that would have shown them still sitting in the wrong section, and was caught two days later by someone else's count.

### Resume report format

One line per finding, in the report: `closed — {commit}` or `open — {why}`. Never omit a finding that stayed open. **A finding that enumerates conditions (a), (b), (c)… is not one finding but one per letter**: give each its own line, by its letter, and never merge them into a single `closed`. A round that applied (b), (d) and half of (a) — and silently dropped (c) — reported the finding closed and came back; there is no judgement call about which parts of an enumerated list apply, and a condition you believe is wrong is answered in writing, not skipped.

- **Resuming a branch marked `ALREADY EXISTS`: the scope is every finding in every NEEDS WORK comment on the PR (`gh pr view $PR --comments`), plus whatever the resume prompt adds — a prompt can add scope, never remove it.** Check each finding against the current branch head, not against a commit message; report it in the Resume report format above.
- **A resumed branch rewrites the PR body to the current head (`gh pr edit $PR --body …`), not only the report and the review comment.** Criteria table including any criterion added since the first round, the full Changes list against `git diff --stat {base}...HEAD`, and the deviations as they are now — a deviation the round reversed is deleted, not left standing. The body of a squash-merged PR becomes the commit message on the base branch and stays there for good: a round that updated the report and the comment and left the body behind published, permanently, a description of work it had just replaced (a stale body claimed the opposite liveness model from the one delivered, named two tests that no longer existed and omitted three changed files).
