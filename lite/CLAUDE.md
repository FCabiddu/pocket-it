# Global rules (v7, 2026-09-28 — errors count only when there is damage)

Reply in the user's language; file names, commands and agent names stay in English.

## No inventions, no shortcuts
- Every instruction (of these rules, of the agent, of the task) is carried out in full and in the written order. Going fast is no reason to skip a step: if a step looks useless, say so to the user, do not skip it.
- State nothing you have not seen. A fact about a file, a test, a PR, a CI run or the code is stated only after reading it or checking it with a command; otherwise say «not verified».
- A check counts only if it could have given the opposite result. Before trusting an empty search or a filtered or truncated output, ask whether it would have shown what you are looking for; in doubt, read the file at the right spot.
- If you notice you skipped a step or stated something unverified, tell the user at once and redo the step.

## How work is done
- **Small work**: you do it yourself, in the session, on a branch. It is small work if all three hold: it touches at most 5 files, no new technical choice is needed (no new entry in the directives), there are no requirements to ask the user. Otherwise it is a feature. In doubt, tell the user with your proposal. Run the tests of the code you touch and of what uses it, then open a PR and merge it.
- **Feature**: every step is done by a dedicated agent; the main session launches the agents, carries questions to the user and reports.
  0. Only at the start of a project (its first feature with this flow) run `~/Desktop/agents/lite/bin/project-ready.sh` in the repo, once: it checks that the project has its directives, the `E2E:`, `Deploy from main:` and `Commands only with approval:` lines in `CLAUDE.md`, `scripts/pre-merge.sh`, `scripts/e2e.sh`, `scripts/e2e-select.sh` and `.claude/settings.json` with the Claude Code sandbox on the agents' commands (`lite/templates/README.md`). If it is red, the `architect` creates the missing pieces from the templates in `lite/templates/` in a PR, before the requirements or together with them, and the `security` agent does the first audit of the whole project (Audit job, principles in `lite/docs/security.md`): the holes it finds become a correction feature, which the user prioritises with the others. No wave starts with `project-ready.sh` red.
  1. `analyst` turns the request into requirements (`docs/features/<slug>/requirements.md`) and assesses feasibility on the code. You ask its questions to the user, then pass the answers back (SendMessage). The user approves the requirements: it is the only document they have to read.
  2. `architect` decides the technical solution (`docs/features/<slug>/technical-design.md` as the index, one file per topic in `technical-design/`) and keeps the project's directives file up to date. It can start together with the analyst on the technical points.
  3. `task-writer` writes small tasks (one PR, one kind of work, criteria with their command) split into waves. First one launch for the plan (list of tasks and waves), then one launch per wave or group of at most 5 tasks, in parallel, each in its own worktree. The `architect` checks every group against the design before it starts; tell the user only how many tasks and waves there are.
  4. At the start of the wave create the branch `wave/<slug>-<n>` from main (`git push origin origin/main:refs/heads/wave/<slug>-<n>`). For every task one `developer`, in its own worktree created from that branch (`worktree-new.sh <branch> wave/<slug>-<n>`), which runs only the fast tests (unit, lint, typecheck) and opens the PR towards the wave branch; in parallel only the tasks of the same wave.
  5. One `reviewer` for every PR as soon as it is ready: it reads the code and the results reported in the PR, without rerunning tests (typecheck, lint and unit tests are rerun by the project's `scripts/pre-merge.sh` before the merge, if present). If it asks for changes, pass them to the same developer (SendMessage), then back to the reviewer. When it approves, merge with `~/Desktop/agents/lite/bin/merge-pr.sh <PR>` into the wave branch: it removes worktree and branch.
  6. With every PR of the wave merged into its branch, launch in parallel, each in its own worktree created from the wave branch, the `tester` on the task `E2E-<n>` (it writes the E2E and runs them once, together with those covering the files the wave changed) and the `security` agent (Wave job: it looks for the holes the wave's diff opened). Developer and reviewer never run E2E. The app-bug lines of the tester's report and the security findings are fixed all together, then one single `RERUN` to the tester and a new launch of the security agent:
     - lines pointing at the same app files go to one `developer`, all in the same task; groups with different files to different developers, in parallel, each in a worktree created from the wave branch; reviewer and `merge-pr.sh` as in step 5;
     - when every fix is merged into the wave branch, send `RERUN` to the tester once only;
     - if a line says a choice is needed that the design did not make, it goes to the `architect`, and to the user if there is something to decide;
     - after 2 fix rounds with the same test still red, stop and report to the user.
     With `E2E GREEN` the tester's PR goes through the reviewer and `merge-pr.sh`; then open the PR from `wave/<slug>-<n>` to main. If the `security` agent (relaunched on this commit, if it changed after its sign-off) says `SECURITY OK`, run `~/Desktop/agents/lite/bin/security-ok.sh <PR>` and merge it with `merge-pr.sh`, which stops without that sign-off. Only a wave with green E2E and the security sign-off reaches main.
     Exception: if the project's `CLAUDE.md` says `E2E: at release`, the E2E do not run at the end of the wave: the `tester` writes and updates the specs without running them (checks that need no server) and reports `E2E WRITTEN`; its PR goes through the reviewer and the wave goes to main with `merge-pr.sh` (pre-merge green and security sign-off), with no `RERUN`. The E2E run only in the round before the project's release (`scripts/release.sh`, if present), when the user says a release is being prepared.
  7. With the wave on main and the error check done (damage recap included), run `~/Desktop/agents/lite/bin/clean-wave.sh <slug> <wave> <PRs of the wave's tasks>`: it removes the wave's tasks from main (on the last wave also `tasks/<slug>` and `docs/features/<slug>`) with a PR it merges by itself, and the worktrees and branches left over from the wave (`sec/`, `test/`, `tasks/`, `rev-`), skipping those with uncommitted changes. If it stops, report why.
  The launch prompt carries only the task's information (files, PR, what to check) and the user's words, kept apart from the main session's proposals; the procedures live in the agents' files.
  When you launch a wave, tell the user which agents start and on what. If an agent has been working for more than 20 minutes, look at what it is doing and report it in one line.
  The main session writes no code during a wave: if a task gets stuck, a developer takes it over with more precise instructions, or it goes back to the task-writer or the architect.
  If a developer, tester or task-writer comes back without a finished report (turn limit, interruption), do not start over: relaunch the same agent on the same worktree with «Resume from NOTE.md». These agents commit locally at every finished criterion, spec or task and keep their progress in `NOTE.md` (outside git).
- **Git**: never push to main, always branch + PR. A branch is updated by merging its base, never by rebasing (force push is blocked). Approved PRs are merged by you, unless the user asks for «draft». A production deploy happens only on explicit instruction. With the sandbox on (the project's `.claude/settings.json`) the remote is HTTPS and `gh` is called on its own, on one line (PRs with `--body-file`): inside a pipe, `$(...)` or `cd` it stays in the sandbox and fails.
- **Where files live**: everything the agents produce lives in the project it belongs to. You create the worktrees, before launching the agent, with `~/Desktop/agents/lite/bin/worktree-new.sh <branch>` (for the reviewer `--review <PR>`), and pass the path in the prompt as `Worktree:`; never `isolation: "worktree"`.

## Errors and rules
At the end of a wave run `~/Desktop/agents/lite/bin/errors.sh --wave <slug>-<n>` in the repo: it shows only the errors that arrived after the previous run and the summary of the agent launches (durations, turns, tokens, outcomes, who is near the turn limit or compacted), and appends the wave's row to the board `docs/recap/metrics.md` (tasks, PRs, review rounds, reruns, launches, duration, tokens). Read it together with the agents' reports and split what you find into two groups:
- **Damage**: lost work, data or a database touched without consent, money spent without being asked (for example paid AI calls), a push to main, wrong code that reached main, a task stuck with no way out.
- **Friction**: everything else (a permission denied and then overcome, an agent stopped and restarted, a busy port). It is not analysed and not fixed. One line goes in `docs/recap/friction.md` (date, what, who), in the next docs PR together with the board row (with `damage` and `friction` written in place of the `?`), with no dedicated PR. When the same friction appears for the third time in the file, it becomes damage. A command that failed once and then succeeded (usually a red test during the work) is not recorded, unless the cause is external (port, permission, network): then it is friction, and for the third time the same cause counts.

If there is no damage, no recap is written and the next wave starts. For every damage write `docs/recap/<date>-errors.md` and follow these steps, in this order:
1. **The fact**: reproduced or read in the log, otherwise «not verified».
2. **What is removed**: the conflicting or duplicated instructions, so that only one remains, where it is read at the right moment.
3. **Which tool prevents it** (script, hook, check in the code, permission), with a test that can fail.
4. **A rule** only if 2 and 3 are not enough; it says what it replaces, and goes in the file of whoever must follow it.
Then one problem at a time with the user: explanation, approval, PR, merge. While the feature is in progress only damage to security, data, money or work is discussed at once; the rest waits for the end of the feature.

## Reporting
Plain and short. In long jobs write only at the end of a block, in 3-4 lines. Before merging or installing changes to rules and agents, show them to the user.
