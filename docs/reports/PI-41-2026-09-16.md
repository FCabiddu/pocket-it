# PI-41 — verify.sh tells a defect the PR introduced from one it inherited

**Branch**: task/pi-41-verify-base-red-attribution · **Label**: DevOps · **Risk**: high · **PR**: #83

## What changed and why
A failing check is re-run **once**, in a second throwaway worktree at the tip of `origin/<base>`, and the verdict says whose defect it is. The caller reads the **exit code**: `0` green · `1` the branch's own red (text still exactly `verify: RED`) · `2` verify could not run · `3` `verify: RED — pre-existing on base (cause: base-moved)`. `1` is the *worse* of the two reds, so a mixed run exits 1: inheriting a defect never excuses introducing one. Three distinct integers, one meaning each, documented in the script header and in CLAUDE.md's table — nothing to confuse. Per failing check the output adds one line: `own …`, `base …` (plus a `note` line stating the granularity) or `warn … attribution unknown: <reason>`.
Cost: the whole block sits inside `if [[ $NFAIL -gt 0 ]]`. A green run creates no second worktree and re-runs nothing.
Honest limit, stated in the script, in the output and in reviewer.md: attribution is **per check, never per assertion**. No heuristic on failure text was attempted — normalising runner output (timings, counts, paths) would have made the motivating case itself read as "own", i.e. a false accusation.
