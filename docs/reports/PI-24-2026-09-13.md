## Why this round
Round 2's delta review (f795086..e334819) found the verifications proved the wrong thing:
1. `getAnimations().map(a => a.finished)` hangs forever when any animation on the page is `infinite` (marquee, pulse), so the A.0 screenshot script never finishes on a real page.

### Six cases reproduced, following only the final text (scratch Playwright harness, Georgia, threshold 0, outside the repo)
| Case | Technique / exclusion | Expected | Measured |
|---|---|---|---|
| Ellipsis, clean | `overflow-x: clip; overflow-y: visible`, generous line-height | 0 | **0** |
| Ellipsis, real vertical cut | same exclusion, tight line-height clipping descenders | ≠0 | **136** |
| `line-clamp`, clean | `clip-path: inset(-1em -1em 0 -1em)`, generous line-height | 0 | **2** (see caveat) |
| `line-clamp`, kept-line cut | same exclusion, tight line-height clipping kept lines | ≠0 | **66** |
| `sr-only`, clean | excluded via `:not()` | 0 | **0** |
| Scrollable container, clean | excluded via `:not()` | 0 | **0** |

Four of six land exactly on the expected class (0 for clean/excluded, non-zero and far larger for a real cut). **Caveat, disclosed rather than hidden:** the `line-clamp` clean case measured 2 differing pixels, not 0. Isolated the cause: the 2 px sit at a single glyph edge and persist unchanged even when `clip-path: inset()` is given an arbitrarily large margin (tested `-999px` on all three open sides) — so they are not content being clipped, they are a rendering-engine artifact of `clip-path` itself (a different compositing/anti-aliasing path than `overflow: hidden`) at that one glyph. Two pixels out of ~113,000 in the region, two orders of magnitude below the smallest real cut measured here (66) or by the reviewer (111). Not a reason to add a threshold — flagging it as a known texture of this specific exclusion technique for whoever tunes it next.
