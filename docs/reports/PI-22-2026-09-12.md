# PI-22 — 2026-09-12 (round 3 after delta review)

## What changed and why
- **Defect A** (`bin/cleanup-merged.sh`). `merge-base --is-ancestor` counted a branch created from a base, with no commits yet, as merged.
  - Round 1 kept a branch only while its tip was on the first-parent line of a base that still exists. The review found the gap (F1): the start point may not be on such a line. Cases: an epic since merged with a merge commit and deleted locally and on origin, a non-base branch since merged, a second-parent sha.
  - Round 2 reads the branch's own reflog, oldest entry first (`history()`), with four verdicts:
    - **own**: an entry that made a commit (`commit*`, `cherry-pick`, `revert`, `am`, `Merge made by`, or a rebase `(finish)` replaying one) is still in the tip's history.
    - **fresh**: a `branch: Created from X` entry and no such commit entry. Kept, reason `no commits of its own (created from X)`.
    - **unknown**: no creation entry and no evidence (reflog missing or expired). Kept, the safe direction.
    - **remote**: created from `origin/<same branch>`, a checkout of pushed work. Removed only when a merged PR's head contains the tip.
  - Only **own** goes through the ancestry test. The topology check (`base_line`) is gone.
- **Same function, kept from round 1.** A merged PR removes a worktree only if its `headRefOid` contains the local tip. A failing `git status` means keep. The dirty check runs before any merge test.
- **Defect B** (`.claude/agents/shared/implementing-common.md` §5, F2). The rule is now executable:
  - First command: record `WT` (toplevel) and `BR` (branch).
  - Every command starts with `cd '<WT>' && [ "$(git branch --show-current)" = '<BR>' ] && …`.
  - Before every file write (file tools included) and every commit, the guard must have run.
  - When it fails: stop and report. No recreating the worktree, no main checkout, no other directory.
- The `docs/SESSION_HANDOFF.md` fact on cleanup-merged was rewritten to describe the reflog criterion.

- **Round 3.** (F1) `branch -c` and `branch -m` carry another ref's reflog, commit entries included. A branch copied from main was read as having main's commits and was removed. Now `Branch: copied …` and `Branch: renamed …` restart the reading, so with nothing after them the verdict is unknown and the worktree is kept. The mutation and the round-2 script both remove the two new states. (F2–F4) §5 simplified:
  - `WT` is noted in the first command, and every shell command starts with `cd '<WT>' && …`.
  - `BR` is noted once, when the branch is the agent's: after §6, or at start for a handed-over worktree.
  - The branch check runs on commits only, with no guard before file edits.
  - Shell paths are relative after the `cd`; file tools use `<WT>/…`.
  - §6 now branches with `git checkout --no-track -b {branch} origin/$BASE`: checking out the base fails inside a worktree while the base is checked out elsewhere, and contradicted §5.
  - Not chased, as the coordinator asked: a live agent on a branch already merged cannot be told from a leftover by any commit criterion. PI-31 (worktree lock) covers it, and the script already keeps locked worktrees.

## Deliberate choices / limits
- A worktree checked out from its remote branch and merged without a PR, or with no `gh`, is kept. An empty pushed branch would otherwise pass the ancestry test.
- A branch moved onto pushed work only by `reset`/`branch -f`, with no commit made here, is kept as fresh. Accumulation is the safe direction.
- A reflog expired past its creation and its commits (about 90 days) is kept as unknown.
