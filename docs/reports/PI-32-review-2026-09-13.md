  - `xargs`

### Finding

**1. Bloccante. `.claude/hooks/guard.sh` `spans_of()`: il valore letterale lo esegue l'editor, che il comando stesso può impostare a una shell.**
Regola violata: il commento TEXT OPTIONS promette «blocking is the safe failure». Qui un push che il giro 1 bloccava passa.

Prova sulla shell, in un repo di prova con un payload innocuo: `GIT_EDITOR=sh git commit --allow-empty -em "touch …/RAN3"` crea il file. Lo crea anche `GIT_EDITOR=zsh git commit -e -F - <<X`. Claude Code esporta `GIT_EDITOR=true`, quindi nella pratica funziona la forma con l'assegnazione.

Verdetti da agente, tutti con giro 1 BLOCK e giro 3 ALLOW:
- `GIT_EDITOR=sh git commit --allow-empty -e -m 'git push origin main'`
- `GIT_EDITOR=sh git commit --allow-empty -em 'git push origin main'`
- `env GIT_EDITOR=sh git commit --edit --message='git push origin main'`
- `GIT_EDITOR=zsh git commit --allow-empty -e -F - <<'X'` con corpo `git push origin main`
- `GIT_EDITOR=sh git commit -e -m 'gh pr merge 8'`
- `git -c core.editor=sh commit -e -m 'git push origin main'`, e lo stesso con `tag -a -e` e `merge -e`
- `GH_EDITOR=sh gh pr create --title 'git push origin main' --body x --editor`

Correzione, sempre per costruzione e senza elencare le shell. La sostituzione avviene solo se:
- `git` o `gh` è la **prima parola** della riga: niente assegnazioni, niente `env`;
- per `git`, il sottocomando segue subito, **senza opzioni globali** (`-c`, `-C`, `--config-env`, `--exec-path`, …);
- **nessun argomento** è `-e`, `--edit`, `--editor` o un gruppo corto che contiene `e` (`-em`).

Righe di test nei due versi:
- BLOCK: i sette comandi sopra
- ALLOW: gli stessi senza assegnazione, senza `-c` e senza `-e`

Nel report va la mutazione «prefisso e `-e` ammessi», che deve rendere rosse le righe BLOCK. Nella sezione Residue va una riga: un hook (`core.hooksPath`) o un file scritto in un comando precedente che esegue il messaggio resta fuori, come ogni testo salvato e poi eseguito in due comandi.

**2. Bloccante per mandato del giro. I template della pipeline passano il testo con `"$(cat <<'EOF' … EOF)"`, e da agente quel testo si legge intero.**
Misura sulla storia di questo repository: ogni messaggio e corpo reale è stato rieseguito da agente nella forma del template. Risultati del giro 3 (identici al giro 1; su `main` sono 0):
- commit con controllo del branch (`implementing-common.md` §4): **4/113** bloccati

- `gh pr comment --body "$(cat <<'EOF' …)"` (`reviewer.md` Step 5, NEEDS WORK): **11/79**

Si blocca quando, dopo una parola `git` qualsiasi nel testo, una riga contiene `push` e `main` (senza backtick in mezzo), oppure quando il testo contiene `gh pr merge`. Esempio reale: il corpo «Uso git worktree.⏎Correzione: un push verso main da agente va negato.» è BLOCK; con `` `main` `` è ALLOW.

Correzione nello stesso PR: il testo si scrive in un file con il tool **Write** e si passa con `--body-file` / `git commit -F`. Attenzione: `cat > f <<'EOF'` in Bash è BLOCK anche lui. I punti da cambiare:
