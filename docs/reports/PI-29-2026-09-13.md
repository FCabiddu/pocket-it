# PI-29 — doctor.sh detects a rewritten or deleted base branch

## What changed and why
Server-side branch protection against a force-push or a delete of the base branch is not available
on every plan (free-tier private repos). `bin/doctor.sh` runs before every agent launch, so it is the
right place to make the damage **visible** — not to prevent it, since prevention is out of its reach —
while it is still recoverable (git keeps the old commit around until a `gc` runs).

Added a new "1b" check in `bin/doctor.sh`, right after the existing `baseBranch` existence check:
- Does a real `git fetch --quiet origin +refs/heads/{base}:refs/remotes/origin/{base}` (the leading `+`
  forces the remote-tracking ref to the live value even on a non-fast-forward, and pulls down the
  objects the later `merge-base --is-ancestor` needs — an `ls-remote`-only check cannot run that
  comparison locally once the branch has moved).
- Fetch fails with "couldn't find remote ref" → **ERROR**, branch deleted on origin (AC3).
- Fetch fails for any other reason (no network, origin gone) → **warn**, never a false error (Notes).
- Fetch succeeds, no commit seen before → records the tip, no report (AC4).
- Fetch succeeds, seen commit is still an ancestor of the new tip → advances the seen commit, no
  report (AC1, normal history).
- Fetch succeeds, seen commit is **not** an ancestor of the new tip → **ERROR** naming the lost commit
  and the exact recovery command (AC2, AC6). The seen commit is deliberately **not** advanced in this
  branch, so the error keeps firing on every subsequent `doctor.sh` run until the branch is actually
  restored.
- If the previously seen commit itself is missing from the local object database (shallow clone,
  pruned) the check cannot compare and says so as a warn, rather than guessing.

The seen commit lives at `<git-common-dir>/pocket-it/base-seen` (one `branch sha` line per base
branch) — `git rev-parse --git-common-dir` resolves to the **same** directory from the main checkout
and from every linked worktree of that repository, and it is never committed (AC5). It was made
absolute in the test helper (`--git-common-dir` returns a path relative to the target repo for a main
checkout, absolute for a linked worktree — same rule doctor.sh itself already used for its own
`os.path.abspath`).

## Tests ↔ criteria
All new cases in `bin/doctor.test.sh` (repos 10–12), against real local git remotes (a bare repo as
"origin", real `--force` push, real `push --delete`), never simulated:
- AC4 — `AC4 first run: base branch not reported` / `AC4 first run: seen commit recorded`
- AC1 — `AC1 normal advance: base branch not reported` / `AC1 normal advance: seen commit follows tip`
- AC2 — `AC2 rewritten base: ERROR names the lost commit` / `recovery command names it` / `exits 1` /
  `seen commit NOT advanced` — plus a mutation test: the same fixture, with the `err(...)` call for
  this branch replaced by `pass`, goes green and drops the "was rewritten" line, proving the four
  assertions above are load-bearing.
- AC3 — `AC3 deleted base: ERROR reported` / `recovery command names the commit` / `exits 1`
- AC5 — a second worktree of the same clone records the seen commit first; the first worktree, which
  never ran doctor before, correctly reads it as a **normal advance** (not a first-ever run) once
  origin moves again.
- AC6 — covered by the "recovery command names it/the commit" assertions above (exact `git push
  [--force] origin {sha}:refs/heads/{base}` string).
- Notes (no false error when origin is unreachable) — `unreachable origin: warn, not ERROR` /
  `no false ERROR` / `warnings never fail doctor`.

## Deviations
None from the task. One gotcha found and fixed in the test fixtures, not in `doctor.sh`: a bare repo's

## Round 2 — review findings, both closed

**Finding 1 (AC3, localisation).** The deleted-branch classification matched the English string
`"couldn't find remote ref"` in `fetch`'s stderr; a gettext-enabled git build (Homebrew, Linux) under
a non-English locale would translate that line, the match would miss, and the branch fell through to
the generic `warn … origin unreachable` — AC3 silently degraded from ERROR to warn. Fixed by removing
all message-text parsing from the decision path: the branch's existence is now checked first with
`git ls-remote --exit-code origin refs/heads/{base}` — exit code `2` is git's own documented,
language-independent "no matching ref" signal — before the real `fetch` even runs. Every git
subprocess in the section also runs with `LC_ALL=C, LANGUAGE=C` (belt and braces for the stderr text
still shown to a human in the `warn` case, which is cosmetic only and never branched on). Verified on
this machine's git (Apple Git 2.50.1, no NLS — confirmed by hand that `LC_ALL=it_IT.UTF-8` does not
actually translate its messages here, so the original bug was not directly reproducible locally) by
running the full rewrite/delete scenario under `LC_ALL=it_IT.UTF-8`/`LANGUAGE=it` and
`LC_ALL=de_DE.UTF-8`/`LANGUAGE=de` and asserting the ERROR still fires in both directions (AC2 and
AC3) — and, structurally, the fix no longer reads `fetch.stderr` for classification at all, so no
future git build can regress it.

**Finding 2 (AC6, the rewritten-branch message).** The old message offered one command,
`git push --force origin {prev}:refs/heads/{base}`, which force-overwrites `{base}` back to the old
tip — discarding any legitimate commit pushed to `{base}` after the bad rewrite — and gave no way to
accept an intentional rewrite (the operator had to read the source to find the internal `base-seen`
cache). The new message: (1) names the exact `git log` commands to see what the rewrite added and
what it dropped; (2) for an accidental rewrite, recovers **without touching `{base}` at all** —
`git push origin {prev}:refs/heads/{base}-recovered-{prev[:12]}` publishes the last known-good commit
under a brand-new ref (purely additive; `{base}` and every local branch are untouched) — leaving the
fast-forward of `{base}` itself as a deliberate, separate human step; (3) for an intentional rewrite,
tells the operator to first confirm `git log origin/{base}..{prev}` is empty (nothing local-only would
be lost) or rescue it first with `git branch rescue-{prev[:12]} {prev}`, then run the new
`bash bin/doctor.sh --accept-base`. `--accept-base` only ever updates doctor's own `base-seen` file —
it never touches a git ref, branch or commit, so by construction it cannot discard local work. Tests:
the suggested recovery command is executed for real (from the clone that actually has the lost
commit) and local branches/HEAD are asserted byte-identical before and after, `{base}` on origin is
asserted still at the bad tip (untouched), and the new ref is asserted to carry the lost commit;
`--accept-base` is asserted to leave HEAD/local branches untouched and to make the very next
`doctor.sh` run quiet on that branch.

Checks re-run after the fix: `bash bin/doctor.test.sh` — 57/57 assertions green, exit 0. Full project
`testCommand` (all 10 suites) — all exit 0. `bash -n` on both files — clean.

## Round 3 — review findings, all 4 closed

Root cause of round 2's shortfall, stated once: every fix so far corrected the *text* doctor prints;
nothing ever executed that text. The reviewer's own measurements (recovery leaves doctor red;
`--accept-base` from a project gives exit 127; the locale test passes under the pre-fix code;
`--accept-base` on a deleted base says "try again once reachable") are four instances of the same
gap. The class to close, verbatim from the review: *every command doctor.sh prints must run as-is
from inside any project and bring doctor.sh to green (or say exactly what remains)*.

**Finding 1 (AC6, executable + convergent recovery).** `git push origin {prev}:refs/heads/{base}-
recovered-{prev[:12]}` was additive but pointless: it never touched `{base}`, so doctor stayed red
forever and "then fast-forward {base} back onto it by hand" was not a command — worse, after a
rewrite the two histories are usually not fast-forwardable at all. Replaced with one self-contained
shell one-liner: `git fetch origin && T=$(git rev-parse refs/remotes/origin/{base}^{tree}) && N=$(git
commit-tree "$T" -p refs/remotes/origin/{base} -p {prev} -m '...') && git push origin "$N":refs/heads/
{base}`. The new commit's tree is the CURRENT live tip's tree unchanged (nothing pushed since the
rewrite is altered), with `{prev}` as a second parent, so `{prev}` is an ancestor again; the push is a
genuine fast-forward from the remote's own tip (no `--force`, so it can never collide with a
concurrent push) and needs no checkout or local branch. Verified for real: executed from an unrelated
project clone (no working-tree changes, no checkout), local refs/HEAD byte-identical before/after, a
commit pushed to `{base}` *after* the bad rewrite is confirmed still an ancestor of the new tip, and
the very next `doctor.sh` run is green (not just red with different text). A mutation reverting to the
round-2 side-ref form is executed the same way and proven to leave doctor red.

**Finding 2 (AC6, absolute paths everywhere).** `bash bin/doctor.sh --accept-base` only exists relative
to pocket-it's own checkout; doctor runs from a project root as `bash ~/.claude/agents/pocket-it/bin/
doctor.sh`, so the printed command was never valid outside pocket-it (measured by the reviewer: exit
127). Fixed at the source: the bash wrapper resolves its own absolute path via `BASH_SOURCE[0]`
(`DOCTOR_ABS`) and passes it into the python script; every printed command uses `shlex.quote()` on
that path and on every ref name (a branch name may legally contain shell metacharacters — `(`, `$`,
`'`, `&`, `;`, `|`, etc. — git only forbids spaces, not those). Tests never hand-write the expected
command: they extract the exact string doctor printed (`sed` on the ERROR line) and `eval` it from a
project clone with no `bin/` directory, for both the recovery and the accept path. Two mutations
(reverting recovery to the round-2 side-ref form; reverting accept to the hardcoded relative string)
are each executed the same way and proven to fail — the accept mutation reproduces the exact
production failure ("No such file").

**Finding 3 (AC6, correct deleted-base message).** `--accept-base` on a branch that no longer exists
said "try again once reachable" — false, since origin IS reachable, the branch simply isn't there.
`--accept-base` now calls the same `_classify_base()` helper (ls-remote exit-code based) the main
check uses: `deleted` → says so and how to restore it (`git push origin {prev}:refs/heads/{base}`),
exit 1, `base-seen` untouched; `unreachable` → the "try again" message is correct there and unchanged.
Tests: deleted base (correct message, no "try again", exit 1, `base-seen` unchanged) and the existing
unreachable-origin coverage (repo 12) is unaffected since only the deleted branch changed.

**Finding 4 (locale test not vacuous).** The round-2 `LC_ALL=it_IT.UTF-8`/`de_DE.UTF-8` tests passed
even against the pre-fix (text-matching) code, because Apple git on this machine ships with no NLS
translations at all — `LC_ALL` changes nothing it prints (confirmed by hand). Replaced with a fake
`git` inserted at the front of PATH that always translates fetch's one relevant message ("couldn't
find remote ref" → Italian), regardless of locale — simulating a build where that string is simply
never English. Under that fake: current code (ls-remote-exit-code based) still reports the deleted
branch as an ERROR, unaffected, since it never reads fetch's text at all; a mutation reverting
`_classify_base` to round-2's fetch+regex form degrades to a silent warn under the exact same fake —
proving the new test is not vacuous and the old one was.

Checks re-run: `bash bin/doctor.test.sh` — 63/63 assertions green, exit 0 (57 → 63: +6 net, several
round-2 assertions replaced by stronger ones that execute rather than grep). Full project
`testCommand` (all 10 suites) — all exit 0.
