# PI-25 — doctor.sh non si accorge di due task con lo stesso id

## Cosa cambia e perché

`bin/doctor.sh` costruiva `tasks[tid] = {...}` dentro il ciclo sui file di board:
quando due file dichiaravano lo stesso id in intestazione, il secondo sovrascriveva
silenziosamente il primo nel dict, senza errore né avviso — la stessa classe di bug
già trovata e corretta in `next-wave.sh` (vedi fatto in `docs/SESSION_HANDOFF.md`,
issue #24), mai portata a `doctor.sh`.

Fix: l'estrazione dell'id per il controllo di duplicazione ora usa la stessa regex
di `next-wave.sh` (`^#\s*([A-Za-z]+(?:-[\w.]+)+)`), così i due script derivano l'id
allo stesso modo — un id **dichiarato** in intestazione, mai una supposizione dal
nome file. Un nuovo dict `id_files` accumula, per ogni id dichiarato, la lista dei
file che lo dichiarano; dopo il ciclo, ogni id con più di un file produce un
`ERROR duplicate task id {id}: {percorso1}, {percorso2}, …`. Il vecchio fallback
per intestazioni non parsabili (`os.path.basename(f).split("-")[0]`) resta invariato
per l'uso esistente di `tasks[tid]` altrove nello script (controlli Depends-on,
DEPS.json), ma non partecipa più al controllo di duplicazione: non è un id
dichiarato, solo una supposizione, e farlo partecipare avrebbe potuto produrre falsi
positivi tra file con intestazioni malformate ma nomi simili.

I file EPIC/STORY di riepilogo restano esclusi come già accadeva: sono filtrati dalla
lista `files` prima ancora del ciclo (stesso filtro preesistente), quindi non entrano
mai in `id_files`.

Allineamento chiesto dalle note del task: la regex di derivazione dell'id ora è
letteralmente la stessa usata da `next-wave.sh` (stesso commento a corredo); non
c'era altra divergenza da riconciliare per questo controllo specifico.

## Secondo giro (review PR #50 — Needs Work)

Due finding, entrambi corretti.

**Finding 1 — la regex del primo giro leggeva per id qualunque parola col trattino.**
`^#\s*([A-Za-z]+(?:-[\w.]+)+)` catturava anche un'intestazione come `# Follow-up: …`
(un H1 che comincia con una parola composta, senza cifre) come se fosse un id, e sullo
stesso lato consumava anche la punteggiatura finale di un id vero (`T-2.1.1.` →
`T-2.1.1.` con il punto, invece di `T-2.1.1`). Su una board reale con parecchi file
questo produce falsi ERROR di duplicazione su note che non sono task, oppure falsi
negativi su un vero duplicato che differisce solo per un punto finale.

Fix, in **entrambi** gli script con la stessa regex letterale (nessun modulo condiviso:
sono heredoc python autonomi per progetto, non c'è un meccanismo di import tra loro in
questo repo — la garanzia di accordo è la regex identica, stesso commento, in un solo
commit):
```
^#\s*([A-Za-z]+(?:-[A-Za-z]+)*-\d+(?:\.\d+)*)
```
Un id vero richiede un segmento numerico finale (le forme del repo: `T-{e}.{s}.{t}`,
`T-BUG-{n}`, `QF-{n}`, `PI-{n}`); una parola composta senza cifre non produce più alcun
id (il file viene ignorato dal controllo, esattamente come un file senza intestazione
riconoscibile), e il segmento numerico non consuma un punto finale isolato.

Nuovi test in `bin/doctor.test.sh`: repo6 (due note `# Follow-up: …` — nessun ERROR,
`doctor.sh` verde) e repo7 (`T-2.1.1.` vs `T-2.1.1` — devono estrarre allo stesso id
ed essere segnalati come duplicati, prova che il punto finale non viene più inglobato).
Nuovo test in `bin/next-wave.test.sh` (AC4): due note `# Follow-up: …` più un task vero
→ nessuna delle due compare come id, `next-wave.sh` conta `1 total` (non 3), nessuna
fusione in un falso task «Follow-up».

**Finding 2 — il test di AC3 non era una prova di regressione.** Verificava solo
l'assenza della stringa esatta `duplicate task id PI-19`; una chiave di dedup più
debole (es. prefisso + ultima cifra, che confonde `PI-9` e `PI-19`) avrebbe comunque
stampato `duplicate task id PI-9` e il caso sarebbe rimasto verde. Aggiunto repo5:
board con solo `PI-9` e `PI-19` (nessun altro file), assert che l'intera stringa
`duplicate task id` sia assente e `doctor.sh` esca 0 — qualunque chiave che confonda i
due id lo rende rosso.

**Prova per mutazione (entrambi i finding insieme).** Sostituita la riga
`id_files.setdefault(m.group(1), ...)` con una chiave debole `prefisso + ultima cifra`
e rieseguito `bin/doctor.test.sh`: `AC1 duplicate id is an ERROR with id and both
paths` (stringa esatta non più prodotta), `AC3 regression: PI-9 alone next to PI-19
alone` e il relativo `exit 0` diventano rossi, così come `trailing dot stripped: both
extract to T-2.1.1`. Confermato che i nuovi test intercettano la classe di regressione
descritta dal reviewer. File ripristinato dal backup subito dopo (diff verificato:
solo la riga della regex resta cambiata rispetto al commit precedente).

**Verifica su board reale e grande (letta in sola lettura, fuori da questo repo, mai
scritta).** Nessuna board di dimensioni comparabili dentro `pocket-it` stesso (20 file);
usata una board reale di un progetto a cui ho accesso in lettura, circa 400 file di
task dopo il filtro EPIC/STORY. `bash bin/doctor.sh` (versione corretta) su quella
board: **0 error(s)**, 15 warning (tutte pre-esistenti e non legate ai duplicati:
formato legacy di alcuni file `*_DEPS.json`, sottosezioni mancanti in un TAD), 412 task
file. Confronto quantitativo, solo per contare — nessun titolo o percorso di quel
progetto riportato qui: con la regex del primo giro (prima di questo fix) la stessa
board produce **406** id estratti e **1** gruppo di "duplicati", di cui **1** è un id
senza alcuna cifra (esattamente la classe di falso positivo del finding 1); con la
regex corretta gli id estratti scendono a **403** (i 3 file dal titolo composto senza
cifre escono dal conteggio, come devono) e i gruppi di duplicati tornano a **0**. Board
descritta solo per forma e conteggio, come richiesto.

## Terzo giro (review PR #50 — delta Needs Work)

**Il difetto:** la regex del secondo giro (`^#\s*([A-Za-z]+(?:-[A-Za-z]+)*-\d+(?:\.\d+)*)`)
richiedeva un segmento finale **puramente numerico**. Due famiglie di id veri ne
uscivano rotte:
- **ignorati** (nessun id, il task sparisce): un segmento che mescola lettere e cifre,
  prima o dopo il numero — `STYLE-PR1`, `WELCOME-A11Y-1`, `E2E-4`, `T-I18N-2`;
- **troncati** (la regex si ferma al primo non-cifra): `T-1.2.3a` e `T-1.2.3b`
  diventavano entrambi `T-1.2.3`; `QF-10b` diventava `QF-10` — due id reali fusi in
  uno, la stessa classe di difetto che PI-25 deve prevenire, non un falso positivo su
  una nota.

Il secondo giro aveva contato solo gli errori di `doctor.sh` sulla board reale (0),
senza confrontare gli id file per file con `main`: il conteggio non basta, perché un
id troncato che collide con un altro id troncato produce comunque zero errori se
nessuno dei due era già un duplicato prima.

**Fix**, eseguito **da me** prima di adottarlo (non solo accettata la proposta del
reviewer), identico in `bin/doctor.sh` e `bin/next-wave.sh`:
```
^#\s*(?=[A-Za-z][A-Za-z0-9]*-[^\s:]*\d)([A-Za-z][A-Za-z0-9]*(?:[-.][A-Za-z0-9]+)+)
```
Un prefisso che comincia con una lettera, segmenti alfanumerici separati da `-`/`.`,
con l'obbligo (via lookahead) di una cifra dopo il primo trattino, senza consumare
la punteggiatura finale.

**Confronto riga per riga sulla board reale (stesso progetto del secondo giro, letto
in sola lettura, mai scritto, descritto solo per forma e conteggio).** Script
temporaneo (non committato) che replica il filtro file di `next-wave.sh` e applica, a
ogni file, la regex di `main` (quella oggi in `origin/main:bin/next-wave.sh`,
`^#\s*([A-Za-z]+(?:-[\w.]+)+)`) e quella di questa PR, poi confronta l'id ottenuto:

| id assente su `main`, presente sulla PR | 2 |
| id presente su entrambi ma **diverso** (troncamento/fusione — deve essere 0) | **0** |

I 5 casi "perso" sono tutti e soli lo stesso id senza alcuna cifra (verificato:
`any(c.isdigit() for c in id)` è `False` per tutti e 5) — le note senza numero
descritte come unica differenza ammessa. I 2 casi "guadagnato" sono id con un
segmento alfanumerico subito dopo il prefisso (forma `PREFISSO-A11Y-...-1`): la
regex di `main` non li leggeva già oggi (il suo primo segmento è `[A-Za-z]+`, senza
cifre, e in questi id la cifra compare nel primo segmento stesso, quindi `main` non
trova nessuna `-` valida e produce nessun id) — un difetto preesistente su `main`,
non introdotto da questa PR, che la nuova regex risolve come effetto collaterale;
nessuna dipendenza o riferimento a questi due id è oggi bloccato (nessuno dei due è
in stato Todo), riportato solo per completezza del confronto. Zero casi di id
diverso tra i due lati: nessun troncamento, nessuna fusione.
