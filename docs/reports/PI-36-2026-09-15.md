# PI-36 — guard force-push check crossed the command boundary

## What changed and why
`.claude/hooks/guard.sh`'s trailing line was a flat `grep -qE 'git push .* (--force|-f)\b.*(main|master)'`
against the whole (heredoc/string-stripped) command text. Its `.*` reads across an unquoted
`&&`, `;`, `|`, `|&`, `||` or newline, so `main`/`master` belonging to a *different* command
(`gh pr create --base main`, `gh pr merge … --base master`, an `echo`, a `--body` argument, a
`$BASE` variable) was read as the push's own destination. Reproduced: `git push
--force-with-lease origin task/foo && gh pr create --base main …` was blocked as a force-push
to main, although the push targets `task/foo`.

The file already carries a segment-aware push classifier (the Python block above, `segments()`
+ `analyze()`/`classify_ref()`) that tokenises the command on the same boundaries and computes
`BLOCK_FORCE` per segment for every force/destructive form (`-f`, `--force*`, a leading `+`,
`--delete`/`-d`, `--mirror`/`--prune`, an empty-source refspec, `--all` + force, an implicit
push whose current branch is the base). The flat grep duplicated that job, imperfectly, once
per whole command instead of once per segment — so it is **removed**, not patched, per the
task's own note that a line removed is worth more than a longer regex. A comment in its place
documents the force-check's threat model (AC4): adversary = a cooperative agent force-pushing/
deleting/mirroring the base by mistake or to route around review; must block = any push
segment whose refspec(s) replace or remove main/master's history on the remote, regardless of
neighbouring segments; explicitly not covered = the same deliberate-evasion classes the
file-level threat model at the top already excludes.

## Tests ↔ criteria
- **AC1** (a push that does not touch the base stays ALLOW whatever later segments contain):
  36 new cases in `guard.test.sh`, built as a construction — 5 separators (`&&`, `||`, `;`,
  `|`, `|&`) × 6 context shapes (`gh pr create --base main`, an authorized `gh pr merge …
  --base master`, a shell comment naming main, an `echo` naming main/master, a `--body`
  argument naming main, a `$BASE=main` assignment) + the newline separator × the same 6
  contexts.
- **AC2** (a force-push that truly reaches the base is still BLOCK): two named forms not
  previously tested on their own (`--force-with-lease`, `--force-if-includes` alone reaching
  `main`/`master`), plus a symmetric control — the same 5 separators, with the force-push
  really targeting `main` and a harmless task-branch segment after it — proving the fix does
  not launder a real force-push into ALLOW just because a neighbour segment is benign.
- **AC3**: full existing `guard.test.sh` (now 222 `ok`, 0 `FAIL`) and `guard.heredoc.test.sh`
  pass unchanged — no existing case's expectation was touched.
- **AC4**: threat-model comment added in `guard.sh` in place of the removed line (see above).

**Mutation run** (not committed — done by hand against a scratch copy): restored the original
buggy line, re-ran `guard.test.sh` — 25 of the 30 AC1 matrix rows went red (`want ALLOW got
BLOCK`), confirming the new tests fail on the unfixed file. Restored the fix; suite back to
0 FAIL.
