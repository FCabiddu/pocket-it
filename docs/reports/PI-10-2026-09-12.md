# PI-10 — report

## What changed and why
`guard.sh` blocked every `git push` to `main`/`master` unconditionally, but the orchestrator's own
skills prescribe exactly that (board/index/memory updates on the base branch after a wave, or a
task file written before a worktree exists). Added `POCKET_IT_ORCHESTRATOR_PUSH=1`, the same
audit-prefix shape already used for `gh pr merge`: an audit trail, not a technical permission,
that authorizes a plain push (explicit or implicit) to main/master but never a force-push, which
stays blocked for everyone unconditionally.

## Implementation
- `AUTHORIZED_PUSH` flag set from the prefix regex (same shape as `POCKET_IT_USER_MERGE=1`).
- The two static "explicit main" regex blocks are now skipped when authorized.
- The Python branch-resolution block (implicit push, `-C`, `cd` chains) now also detects a force
  flag (`-f`, `--force*`) per push segment and reports `EXPLICIT_FORCE`/`IMPLICIT_FORCE`; those
  verdicts always block, regardless of `AUTHORIZED_PUSH`. Non-force `EXPLICIT`/`IMPLICIT` verdicts
  only block when not authorized.
- The segment regex now also strips a leading `POCKET_IT_ORCHESTRATOR_PUSH=1 ` before matching
  `^git`, so force/implicit-main detection still runs when the segment carries the prefix (without
  this, `PREFIX=1 git push --force` fell outside the `^git` anchor and slipped through — caught by
  a self-authored mutation test, see below).
- The pre-existing standalone force-push regex (line ~139, unconditional, text-only) is untouched:
  it remains a second line of defence for explicit forms.
- Updated `.claude/skills/quickfix/SKILL.md` (two spots: the task-file push in §2, the close-step
  push in §4) and `.claude/skills/run-wave/SKILL.md` (§5 close-the-wave push) to use the prefix.
- **Deviation** (files outside the task's `**Files**:` list): `.claude/skills/intake/SKILL.md` had
  the identical bare `git push -q` on what is the base branch at intake time — the exact bug this
  task describes. Fixed it too and said so here, since leaving it would reproduce "a task file
  never reaches origin" for the very first skill in the pipeline. `deps/SKILL.md` was checked and
  needed no change: its only "push" line is a cross-reference to quickfix's already-fixed one.

## Review fix (delta) — two regressions on AC4, both confirmed and closed
The reviewer found two spellings of force-push that `is_force()`/the refspec parser missed, so the
`POCKET_IT_ORCHESTRATOR_PUSH=1` prefix wrongly authorized them (BLOCK on `main` today, would have
become ALLOW on this branch):
- **F1** — `is_force()` matched `-f`/`--force*` only as a whole token; git's parse-options accepts
  clustered short flags (`-uf`, `-fu`, `-qf`, ...). Fixed: any short-flag cluster containing the
  letter `f` (`re.fullmatch(r'-[a-zA-Z]+', t) and 'f' in t[1:]`) is now treated as force. No other
  `git push` short flag uses `f`, so no false positive.
- **F2** — a leading `+` on a refspec (`+main`, `+HEAD:main`) is itself a force-push in git and was
  never stripped before the destination was compared to `main`/`master`: `+HEAD:main` was
  classified `EXPLICIT` (non-force) because the destination-side comparison already matched by
  accident, but the force flag was never set; `+main` alone matched neither branch at all. Fixed
  with a `strip_plus()` helper applied to the refspec in both the single-positional and
  two-positional branches, before the colon split and the `main`/`master` comparison.

Three total force-push forms git accepts are now covered end to end: `-f` (incl. clustered),
`--force`/`--force-with-lease`, and a leading `+` on the refspec. The pre-existing standalone text
regex (`--force|-f` + `main|master`) is confirmed to *not* catch either F1 or F2's spelling
(verified: no `-f` substring in `-uf`, no force flag/keyword in `+main`) — it is not a backstop for
these, the Python parser is now the only correct line of defence.

Added to `.claude/hooks/guard.test.sh`, all prefixed to prove the prefix does not help:
`-uf origin main`, `-fu origin main`, `-qf origin main`, `origin +main`, `origin +HEAD:main` (all
BLOCK), plus two non-force controls (`-uq origin main` ALLOW, `origin +task/x:task/y` unprefixed
ALLOW — a `+` on a refspec that does not target main/master is not blocked).

Mutation-proved by hand: reverting `is_force()`'s cluster branch turned the three F1 cases red
(`want BLOCK got ALLOW`); reverting `strip_plus()` to a no-op turned the two F2 cases red; both
reverts left every other case green. Full suite re-run clean after restoring the fix: 63/63 in
`guard.test.sh`, and the whole `testCommand` chain (`cleanup-merged`, `worktree`, `doctor`,
`handoff`, `next-wave`, `guard`, `guard.heredoc`) green.

No new deviation, no new env var. Not re-touching the standing header comment at
`guard.sh:29-33` — it already stated "a force-push to main/master is blocked even with the
prefix," which is now true for all three forms instead of two.
