# PI-38 — `gh pr merge --delete-branch` leaves the remote branch alive

## What changed and why

`cleanup-merged.sh` ran after every merge in both skills but only ever judged worktrees and **local**
branches. `gh pr merge --delete-branch`'s own cleanup fails silently in two shapes (from a worktree: aborts
before touching the remote branch; from main with another worktree still on the branch: deletes remote,
not local), so remote branches of merged PRs pile up on `origin` unnoticed.

Added `reap_remote_branches()` to `bin/cleanup-merged.sh`: one `gh pr list --state merged --json
headRefName,headRefOid` call per run, matched against every `refs/remotes/origin/*` ref not currently checked
out in any of this repo's own worktrees and not `protected()`. A remote branch is deleted only when its
current tip equals a merged PR's own recorded head — never by `git merge-base --is-ancestor` (AC3: a squash
merge breaks ancestry by construction, so ancestry would either falsely keep a squashed branch's remote ref
alive or need a second, different code path). Every failure point (`gh` absent, `gh pr list` failing, `git
push --delete` failing) prints one line and returns/continues — never aborts the script, never a long wait.
`drop_branch()` (local branches) was deliberately left untouched: reaping is a fully decoupled pass so it
never competes with, or changes the outcome of, the existing per-worktree local-branch decision.

Measured today directly against pocket-it's own GitHub repo (read-only, no writes): `gh pr list --state
merged --limit 200` → 71 merged PRs; `git ls-remote --heads origin` → 37 non-`main` branches; `comm -12`
between the two → **33 of those 37 are a merged PR's own head, still on origin**. (The task's "30 of 60" is
stale — the PR count has grown since it was measured; today's repo state gives 33/71.) Per the task's own
instruction, **these 33 pre-existing branches are intentionally left alone** — the mechanism is closed here,
the one-time sweep is a separate, later step the user runs after this merges.

## Deviations

- None from the task's AC1–AC5. One extra: `reap_remote_branches()` does not validate the shape of `gh`'s
  global JSON output line-by-line the way the existing per-branch `merged_pr()` does (which treats garbage
  output as "unknown", exit 2). Not one of AC4's three named dimensions (no `gh`, no network, no write
  permission), and the actual failure mode is already safe by construction: a malformed line simply matches no
  real branch/SHA pair, so nothing gets deleted and the script still exits 0. Left as-is to keep the diff to
  what AC4 asked for; noted here rather than silently added.

## Left undone on purpose

- The 33 pre-existing merged-PR remote branches already on `origin` today are **not** cleaned up by this PR.
  The task says explicitly: close the mechanism first, run the one-time sweep separately, after this merges.
